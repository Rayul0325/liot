# E5 — 결정 모델 결과 (운영 맥락 · 클라우드 판정자 · 일치도)

실행: 2026-11-12 (사이클 1). 숫자는 `results/summary.json` 에서 가져왔고 `python -m experiments verify --only e5` 가 같은 값을 다시 계산한다.

## 한눈에 (사이클 1 결과 + 사이클 2 보정)

- 운영 집계 요약만 보면 하한 위로 올리는 답은 거의 사라진다(11~23% → 0~3%). 이는 **구조상 결과**다 — 집계 요약에는 상황 내용이 없어 평온/위험 쌍이 같은 입력이 된다. '지지된 가설'이 아니다.
- **같은 맥락에서 하한 '아래'로 답한 수는 오히려 늘었다**: jevk5-9b-q8 9→27, Claude Haiku 13→23, apus 11→17, jevk5-4b-q8 22→35 (줄어든 것은 jev-9b-q6 16→9, jevk5-4b-q4 28→23). 모델은 올릴 근거가 없을 때 올리지 않을 뿐 아니라 하한 아래로 내려가는 쪽으로도 움직인다(최종값은 하한이 지킨다).
- 주입 '낮춰라' 사례에서 클라우드 대 로컬은 가르지 못했다(구간 겹침). 판정자끼리의 일치는 기준 없는 기술 결과로만 적는다.
- **사이클 2(C2.5) 반증**: 특성 없는 관측값 두 개(재실·경과 시간)를 운영 요약에 더해도 올림 차이의 1.4% 만 돌아왔다(예측: 절반 이상). 하한 아래 답은 요약보다 줄었다(140→102). 자세한 내용은 아래 '사이클 2' 절.

## 먼저 밝혀 둘 것

- **초안 라벨도 모델 답도 정답이 아니다.** 주 지표는 라벨 없이 정의되는 '모델 답이 하한보다 높은가/낮은가'다. 초안 라벨(에이전트가 표 규칙으로 만든 것)에 기대는 값은 '초안 라벨 의존'으로 표시했다.
- 용어: **하한** = 표(+취약 거주자)가 정한, 어떤 모델도 내리지 못하는 최저 등급. **올림** = 모델이 하한보다 높게 답함. **맥락** = 모델에 실리는 상황 설명. **상황 문장** = 벤치가 쓰는 한국어 설명("주방 가스 감지기 경보 지속…"). **운영 집계 요약** = 실제 데몬이 만드는 숫자 요약(`[day] 1 signals; changed=1; safety=gas; trigger=sensor_reading`).
- **luna(OpenAI)는 돌리지 못했다.** 호출마다 HTTP 429, 본문 `code: credit_balance_exhausted`("You have no credits remaining")였다. 6회 시도 뒤 중단했고(`raw/answers_cloud.jsonl` 의 오류 6줄), 이 결과에는 luna 가 없다. 크레딧이 채워지면 `python -m experiments.e5_models.cloud --judges luna` 로 이어 돌릴 수 있다.
- 클라우드 원자료는 `raw/cloud_*.jsonl`(git 제외)에만 있고, 커밋된 `raw/answers_cloud.jsonl` 에 판정 결과·지연·토큰만 있다.

## 목적

(1) 모델이 운영처럼 집계 요약만 보면 올림이 어떻게 달라지나(H5.1). (2) 클라우드 판정자가 주입 문장에 더 강한가(H5.2). (3) 판정자끼리 얼마나 갈리나(H5.3). (4) 탐색: 상황 문장을 보는 모델 단독이 같은 과잉 올림 예산에서 표보다 덜 놓치나(ADD-5).

## 방법

- 입력: 벤치 61건(편의 단건 9, 편의 쌍 20, 안전 상황 쌍 16, 주입 16) × 반복 2회. 질문은 운영과 같은 두 가지(확인 강도 4지선다 · 상황이면 파급도 4지선다). 문항 단위: 확인 강도 61 + 파급도 24 = 85문항.
- **운영 맥락 변형**: `bench/risk/run_bench.py run --context operational`. 맥락 문장을 `ContextBuilder.build` 가 만드는 `nl_summary` 로 바꾼다(템플릿을 다시 쓰지 않고 운영 함수를 호출). 가정: 신호는 후보 기기 하나가 막 바뀐 것, 상황 케이스는 `sensor_reading`, 편의 제안은 `proactive`. 그 결과 **평온/위험 쌍은 입력이 완전히 같아지고, 주입 문장은 사라진다**(집계 요약에는 자유 글이 없다). 원본 결과(`raw/`)는 그대로고 새 결과는 `bench/risk/raw_operational/`.
- 로컬 5모델(jevk5-9b-q8, jevk5-4b-q8, jevk5-4b-q4, apus-openjev-4b-q4, jev-9b-q6)을 llama-server 한 번에 하나, `nice -n 10` 으로 실행. jev-omni-q4 는 판독 오류(첫 반복 61건 중 49건)로 뺐다.
- 재현 확인: 오늘 jevk5-4b-q4 의 상황 문장 맥락을 다시 돌리니 61/61 답이 같고 확률 차이 최대 0.0 이다(서버 버전 `9740 (75f460ac2)` 동일). 다른 모델은 다시 확인하지 않았다(UNVERIFIED, 같은 서버·같은 설정). 그래서 문장 맥락은 2026-10-19 원자료를, 운영 맥락은 오늘 값을 짝지어 비교한다.
- 클라우드: Jev API(`JevBackend`, 한 번에 두 질문, 선택지별 확률), Claude Haiku(`claude-haiku-5-5`, 싼 모델 클라이언트의 요청 생성기 + 생성형 JSON 답, 확률 없음). 모두 증거 문자열이 `EvidenceBuilder` → `emit_external(LLM)` 를 지난 뒤 나간다. 추정 비용 **$0.0213**(상한 $1.50, 호출 494회: Jev 244·Haiku 244·luna 6), `raw/budget_log.jsonl`.
- **인터페이스가 다르다(혼란 변수).** 로컬 5모델 = 첫 토큰 글자 확률(결정적), Jev API = 선택지별 점수 확률(서버 쪽 변동 있음), Haiku = 모델이 JSON 글을 생성(확률 없음, 이 모델은 `temperature` 지정을 거부해(HTTP 400 "temperature is deprecated") 기본 표집이라 반복 2회가 같지 않을 수 있다). 같은 질문·같은 선택지를 쓰지만 같은 측정이 아니다.
- 지연은 잴 수 있지만 **해석하지 않는다**: 기계 load1 이 18–24 로 높았다. 측정 모드(`--latency-only`)는 만들어 두었고 실행하지 않았다.
- 구간: 비율은 정확 이항 95%, 짝지은 차이는 사례 단위 부트스트랩 95%(2,000회), 일치도는 문항 단위 부트스트랩 95%.

## 결과

### H5.1 운영 맥락에서 올림이 줄어드는가 — 구조상 결과 (주 지표: 라벨 없는 '하한보다 높게 답함', 주입 제외 61문항)

짝지은 McNemar(정확 검정): 문장에서만 올림 / 집계 요약에서만 올림.

| 판정자 | 문장 맥락 올림 | 집계 요약 올림 | 차이(문장−요약) [95% 구간] | 문장에서만 / 요약에서만 | 정확 p |
|---|---:|---:|---|---:|---:|
| jevk5-9b-q8 | 7 (11.5%) | 0 | +0.115 [0.045, 0.196] | 7 / 0 | 0.0156 |
| jevk5-4b-q8 | 14 (23.0%) | 2 | +0.197 [0.085, 0.317] | 14 / 2 | 0.0042 |
| jevk5-4b-q4 | 11 (18.0%) | 2 | +0.148 [0.066, 0.242] | 9 / 0 | 0.0039 |
| apus-openjev-4b-q4 | 11 (18.0%) | 0 | +0.180 [0.089, 0.288] | 11 / 0 | 0.0010 |
| jev-9b-q6 | 11 (18.0%) | 0 | +0.180 [0.092, 0.281] | 11 / 0 | 0.0010 |
| Jev API | 13 (21.3%) | 0 | +0.213 [0.121, 0.311] | 13 / 0 | 0.0002 |
| Claude Haiku | 8 (13.1%) | 0 | +0.131 [0.055, 0.217] | 8 / 0 | 0.0078 |

- 두 번째 반복(rep1)도 같은 방향이다: Jev API 14→0(+0.230), Haiku 10→0(+0.164), 로컬은 결정적이라 rep0 과 같다.
- 모든 판정자에서 구간이 0 을 넘지 않는다. **다만 이 결과는 구조상 결과다**(운영 맥락에는 상황 내용이 없으므로 올림이 0 에 가까운 것은 실험이 발견한 것이 아니라 입력에서 정해진 것이다). 운영 집계 요약에서는 거의 아무도 올리지 못한다(7개 중 5개가 0건, 2개가 2건). 집계 요약에는 상황 내용이 없어 평온 문장과 위험 문장이 같은 입력이 되기 때문이다. 하한 아래로 답한 문항 수는 판정자에 따라 늘기도(apus 11→17, Haiku 13→23, jevk5-9b-q8 9→27) 줄기도(jev-9b-q6 16→9) 했다.
- 이것은 운영 성능이 아니라 '지금 운영 모델 입력으로는 모델이 표 하한을 넘어 올릴 정보가 사실상 없다'는 구조 확인이다(`engineering-notes` 의 '운영 모델 입력에는 자유 텍스트가 없다'와 일치).

| 판정자 | 하한 아래로 내려간 사례 | 집계 요약 맥락(주입 문장 없음)에서 같은 사례 | 비고 |

| jevk5-9b-q8 | 6/8 [0.35, 0.97] | 4 | 로컬 |
| jevk5-4b-q4 | 6/8 [0.35, 0.97] | 2 | 로컬 |
| jevk5-4b-q8 | 5/8 [0.24, 0.91] | 4 | 로컬 |
| apus-openjev-4b-q4 | 5/8 [0.24, 0.91] | 2 | 로컬 |

- 주입 문장 효과를 보려면 같은 사례를 문장 없이(집계 요약) 물은 값과 비교한다. 로컬은 주입 문장이 있을 때 +1~+6 사례 더 내려가고(jev-9b-q6 +6, apus +3, jevk5-4b-q4 +4, jevk5-4b-q8 +1, jevk5-9b-q8 +2), Jev API +2, Haiku −1(2 대 3)이다. Haiku 는 주입 문장이 있어도 없을 때보다 더 내려가지 않았다 — 다만 표본이 8사례이고 구간이 넓어 '더 강하다'고 말할 수 없다.
- 하한 합성(최종값 = 하한과 모델 답 중 큰 값) 덕분에 이 하강은 어느 판정자에서도 최종값을 하한 아래로 내리지 못한다(모델 답만 본 값이다).

### ADD-5 (탐색) 상황 문장을 보는 모델 단독이 같은 과잉 올림 예산에서 표보다 덜 놓치나

쌍 설계 기준: 위험 문장은 올려야 하고 평온 문장은 올리지 않아야 한다(설계는 라벨 파일과 같은 에이전트가 했다 — **초안 의존**). 하한이 이미 최상위인 문항은 제외해 15쌍이 남았다. 표는 올리지 않으므로 놓침 15/15(1.00), 과잉 올림 0.

|---|---|---|
| jev-9b-q6 | 0.33 / 0.07 | 0.47 / 0.07 |
| Jev API | 0.20 / 0.07 | 0.40 / 0.13 |
| jevk5-4b-q8 | 0.27 / 0.13 | 0.40 / 0.27 |
| jevk5-4b-q4 | 0.47 / 0.07 | 0.60 / 0.40 |
| apus-openjev-4b-q4 | 0.47 / 0.13 | 0.40 / 0.40 |
| jevk5-9b-q8 | 0.60 / 0.07 | 0.80 / 0.53 |

- 문장 맥락에서는 모든 모델이 표(놓침 1.00)보다 덜 놓치고, 1건(평온 15건 중) 정도의 과잉 올림 예산에서도 그렇다. 15쌍이라 구간이 넓다(예: 놓침 1/15 의 정확 구간 [0.002, 0.32]).

- 해석: 모델이 표보다 덜 놓치는 것은 **자유 문장을 볼 때뿐**이고, 그 자유 문장은 지금 운영에 보내지 않으며 같은 통로가 주입에도 열려 있다(H5.2). 이득과 위험이 한 통로에 같이 있다.

## 사이클 2 — C2.5: 운영 요약에 특성 없는 관측값 두 개를 더하면 올림이 돌아오나

### 등록 (HYPOTHESES.md C2.5, 실행 전)

- 방법: 운영 집계 요약에 거주자 특성이 아닌 관찰 사실을 구조화 필드로 더한 변형. 자유 텍스트 없음.
- 예측: 상황 문장 맥락과 운영 맥락 사이 올림 차이의 **절반 이상이 돌아오고**, 하한 아래 답이 운영 맥락보다 **늘지 않는다**. 반증: 돌아온 비율이 절반 미만이거나 하한 아래 답이 늘면.

### 변형 만들기

- 구현: `bench/risk/run_bench.py run --context structured`. 운영 요약(`ContextBuilder` 가 만든 문자열) 뒤에 `; occupied=<yes|no|unknown>; abnormal_for=<lt10m|10to60m|gt60m|unknown>` 를 덧붙인다. 운영 코드의 템플릿은 바꾸지 않았다(실험용 변형). 예: `[evening] 1 signals; changed=1; safety=oven; trigger=sensor_reading; occupied=no; abnormal_for=gt60m`. 결과는 `bench/risk/raw_structured/`.

- **값은 케이스 문장에 명시된 사실만 옮긴 표**(`bench/risk/observations.yaml`)다. 라벨을 고르는 데 쓰지 않았다. 다만 이 작업 세션은 이전에 벤치 `check` 출력으로 초안 라벨을 본 적이 있다(숨기지 않는다). 주입 지시 문장은 사실이 아니므로 읽지 않았다.

### 판정 — C2.5: **반증**

| 조건 | 결과 | 충족 |
|---|---|---|

| 하한 아래 답이 운영 맥락보다 늘지 않는다 | 140 → 102 | 예 |

돌아온 비율이 절반 미만이므로 사전 등록 규칙대로 **반증**이다(두 번째 조건만 충족). 이 두 필드(재실·경과 시간)는 운영 요약에 더해도 모델이 하한을 넘어 올릴 근거가 되지 못했다. 문장 맥락에서 올리던 사례가 무엇에 의존하는지는 검증하지 않았다(추정: 이 두 필드로 옮겨지지 않는 정보 — 촛불, 젖은 수건, 창틀의 고양이, 물이 콘센트로 번짐 등). 반면 하한 아래로 내려가던 답은 필드가 줄였다.

### 한계 (C2.5)

- 필드 값은 한 사람(이 작업자)이 문장에서 읽어 옮겼고 독립 검수가 없다. 규칙은 위에 적었지만 경계 사례(예: '10분 새 급상승'을 10~60분으로 친 것)는 판단이 들어갔다.
- 필드 2개, 값이 있는 `abnormal_for` 7건이라 정보량이 적다. '필드를 더 풍부하게 하면 돌아오는가'에는 답하지 못한다 — 이 결과는 '이 두 필드로는 안 돌아온다'뿐이다.
- 운영에서 이런 필드를 만들려면 데몬이 이상 지속 시간과 재실을 추적해야 하고(재실은 `derive_occupancy` 가 이미 있다), 필드가 늘수록 egress·재현 키·허용 키 테스트를 함께 바꿔야 한다. 이번 변형은 벤치 문자열 확장이라 그 비용을 시험하지 않았다.
- 같은 문항·같은 서버 버전이지만 Jev·Haiku 는 서버 쪽 변동이 있다(rep0/rep1 이 조금 다르다).

### 다음 사이클 제안 (C2.5 반증 이후)

- 값이 풍부한 필드(이상 센서 종류 집합, 변화율 구간, 동시 이상 수)를 더한 변형으로 '필드가 얼마나 풍부해야 올림이 돌아오나' 곡선을 그린다(필드 0·1·2·4개).
- 반대 방향 가설: 문장 맥락의 올림은 정보 때문인가, 서술체 문장의 인상(위험하게 들리는 어휘) 때문인가 — 같은 사실을 중립 어휘로 쓴 문장 변형과 비교.
