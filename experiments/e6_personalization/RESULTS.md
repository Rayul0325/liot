# E6 개인화·적응 실험 (H4.1, H4.2 = P5, H4.3)

## 목적

LIOT 의 개인화(알림 응답으로 선호를 배우는 규칙과 '[그만해] 뒤 같은 제안을 30일 쉬는 규칙')가 60일 동안 실제로 도움이 되는지, 거주자의 선호가 15일째에 바뀌면 따라가는지, 확인 방식 A·B 가 수락에 영향을 주는지를 대안과 같은 조건에서 비교한다. 결과가 LIOT 에 불리해도 그대로 적는다.

용어
- **도움 제안**: 그날 그 거주자의 숨은 선호로 보면 받았을 때 수락할 만한 제안(수락 확률 0.5 이상인 장면). 시스템은 이 정보를 보지 못한다.
- **잘못 꺼진 도움 제안**: 그 장면이 도움 제안인데도 선호 때문에(그만해로 쉬는 중·점수가 '아무것도 안 하기'보다 낮음·보내지 않음 판정) 그날 하루 한 번도 거주자에게 가지 않은 (날, 장면) 한 건. 쿨다운·시간당 상한 같은 모든 방식이 똑같이 받는 기본 제한은 뺐다.
- **쓸데없는 알림**: 거주자가 싫어하는 장면인데 폰으로 보낸 알림.
- **게이트**: '[그만해] 뒤 30일 쉬기' 규칙(`recently_rejected`).
- **모아보기(digest)**: 급하지 않은 제안을 한데 모아 보여 주는 칸. 실제 데몬은 이것을 거주자에게 전달하지 못한다(`docs/tracking/findings.md`).

## 방법

시뮬레이터 `liot/day_sim.py` 의 연구용 옵션(커밋 `f593c06`)으로 진짜 `LiotService` 를 15분 단계로 60일 돌렸다. 거주자는 확률 모델이다(아래 가정). 30일 결과는 같은 60일 실행의 앞 30일이다(대본·거주자 난수·센서가 씨앗에 따라 결정적이라 앞부분이 같다).

**조건**: 거주자 성향 3종 × 학습 방식 8종 × 확인 방식(A·B) × 씨앗 10개, 60일, 15일째에 일부 장면의 선호가 뒤집힌다. 하루 표본은 씨앗당 1건이고 구간은 씨앗(성향을 합칠 때는 성향×씨앗 쌍)을 다시 뽑는 95% 부트스트랩이다. 총 1,080회 실행(`raw/runs.jsonl`, 7 MB).

| 변형 | 내용 | 실행 수 |
|---|---|---|
| main | 설계 전체. 모아보기는 22시에 80% 확률로 연다(시뮬레이터 가정) | 480 |
| zerofat | 피로·수고 계수 둘 다 0 (H4.3 통제) | 60 |
| fatonly / effonly | 피로만 / 수고만 켬 (H4.3 분해) | 60 / 60 |
| tray0 | 실제 데몬처럼 모아보기를 아무도 열지 않음 | 240 |
| likepure | 좋아하는 장면은 잘못 눌러 [그만해]를 누르는 일이 없음(민감도) | 180 |

**학습 방식(팔)**
| 이름 | 설정 |
|---|---|
| none | 학습 0% + 30일 쉬기 없음 (정적 시스템) |
| explicit_only | 학습 0%, [그만해] 뒤 30일 쉬기만 (ADD-4: 명시적 버튼만) |
| lr10 / lr30 / lr60 | 학습률 10% / 30%(운영) / 60%, 30일 쉬기 있음 |
| permanent | 운영 학습 30% + [그만해]하면 끝까지 차단 |
| no_gate | 운영 학습 30%, 30일 쉬기 없음 |
| explore7 | 운영 + 7일마다 하루 쉬기를 풀고 부정 쪽으로 배운 선호를 중립으로 되돌려 다시 제안 |

**거주자 성향**(15일째 바뀌는 것)
- 거부형: 환기는 좋아하고 공기청정기는 60% 확률로 [그만해]를 누름 → 15일째 공기청정기를 좋아하게 됨.
- 무시형: 공기청정기를 싫어하지만 거의 누르지 않음(무시) → 15일째 좋아하게 됨.
- 뒤바뀜형: 공기청정기를 좋아하고 환기는 싫어함 → 15일째 정반대.

**가정(모두 시뮬레이터 설정이며 근거 자료가 아님)**: 알아챔 90%, 반응 지연 1~4단계(15분 단위, 50·25·15·10%), 피로 0.15(부하가 1이면 알아챔·누름이 1/1.15), 부하 반감기 4시간, 확인 강도별 수고 비용 0.12(none 0 · light 1 · explicit 2 · double 3 단위), 좋아하는 장면은 80% 수락·5% [그만해], 싫어하는 장면은 10% 수락·60% 그만해(거부형)·5%(무시형), 모아보기 열람 80%. 안전 알림의 확인은 옛 방식(다음 단계 [괜찮아요])을 그대로 둬 피로 모델에서 뺐다.

**지표**: 주 지표는 (1) 하루 수락된 도움 제안 수, (2) 하루 잘못 꺼진 도움 제안 수. 수락률은 거절된 것을 안 보내면 저절로 오르므로 보조로만 쓴다. 모아보기는 따로 본다.

**회복의 정의**: 사전 등록 문장(수락된 도움 제안이 변화 전 수준의 80% 로 돌아오는 날)을 그대로 쓰면 성향 둘(거부형·무시형)에서는 변하지 않는 장면의 수락만으로 이미 기준을 넘어 의미가 없다(표의 '문자 그대로' 열이 거의 다 6일). 그래서 주 지표를 둘로 바꿨고 이 변경을 한계에 적었다. (a) **다시 수락**: 바뀐 뒤 새로 도움이 된 장면을 처음으로 수락한 날까지의 일수(바뀐 날=0), (b) **정적 시스템 대비 회복**: 새로 도움이 된 장면의 하루 수락이 정적 시스템(none)의 80% 로 돌아오는 날(7일 이동평균). 관찰 기간은 바뀐 뒤 45일이다.

읽는 법
- 학습 없음(none)이 수락된 도움 제안을 가장 많이 만든다. 그 대가로 쓸데없는 알림이 하루 0.19건(운영 0.06건의 3배)이다.
- **쓸데없는 알림을 줄이는 것은 학습이 아니라 [그만해] 버튼과 30일 쉬기다.** lr30 과 explicit_only 의 쓸데없는 알림 차이는 0.00 이다. 학습을 더 얹으면(lr30) 도움 제안 수락이 하루 0.13건(약 15%) 줄고 잘못 꺼진 도움이 하루 0.38건 늘기만 한다.

- 잘못 꺼진 도움의 큰 몫은 거주자가 좋아하는 장면을 가끔 잘못 눌러(5%) 30일 쉬기가 걸리는 데서 온다. 좋아하는 장면에는 잘못 누름이 없게 한 민감도 실험(likepure)에서는 lr30 의 잘못 꺼진 도움이 31~60일에 0.03 으로 떨어지고, 수락된 도움 제안은 none 과 explicit_only 에 가까워진다(15~30일 0.85 대 1.15·0.96). 그래도 학습 30%는 얻는 것이 없다.

### H4.2 = P5 선호가 바뀌면 따라가는가 (조건 B)

바뀐 뒤 새로 도움이 된 장면을 **45일 안에 한 번이라도 다시 수락한 씨앗 비율**(중앙 일수). 그림: `figures/reaccept_fraction.png`, 시계열: `figures/accepted_helpful_timeline.png`.

|---|---|---|---|---|
| none | 1.00 (5.5일) | 1.00 (5.5일) | 1.00 (0일) | 1.00 (1.5일) |
| explicit_only | 1.00 (18일) | 1.00 (5.5일) | 0.90 (17일) | 0.97 (17일) |
| lr30 (운영) | 1.00 (18일) | 1.00 (5.5일) | 0.90 (17일) | 0.97 (17일) |

| explore7 | 1.00 (17일) | 1.00 (5.5일) | 1.00 (9.5일) | 1.00 (10일) |

정적 시스템 대비 회복(위와 같은 읽는 법, 합침): none 1.00 (6일), explicit_only·lr10·lr30 0.90 (18일), lr60 0.67 (17일), permanent 0.30 (6일), no_gate 1.00 (9일), explore7 0.87 (17일). 모든 성향·조건에서 기준(정적 시스템의 80%)은 도달 가능했다(`reachability`).

- 30일 쉬기가 있는 팔(explicit_only·lr10·lr30·explore7)도 45일 안에 대부분 회복한다. 다만 거부형·뒤바뀜형에서는 중앙값이 17~18일로, 30일 쉬기가 없는 팔(5.5~7.5일)보다 **약 10~12일 늦다**. 이유: 싫어하던 때의 [그만해]가 1~3일째에 걸려 30일이 지난 31~33일째에야 풀린다.
- 영구 차단은 [그만해]를 눌렀던 성향(거부형·뒤바뀜형)에서 45일 동안 한 번도 회복하지 못한다. 학습 60%도 뒤바뀜형에서 20% 만 회복한다.
- 7일마다 재제안(explore7)은 다시 수락 시점을 앞당기지만(뒤바뀜형 9.5일, 합침 10일) 하루만 풀리므로 그 뒤에는 다시 쉬기에 걸려 하루 수락량은 운영보다 약간만 높다(위 표 +0.11).
- 무시형은 [그만해]를 누르지 않으므로 쉬기에 걸리지 않고, 학습이 약해 5.5일에 회복한다. 즉 암묵 학습(만료)은 30%에서 선호 변화를 막지 못한다.

### H4.3 확인 방식 A·B 와 수락 (모델 의존 결과)

수락률은 **두 조건이 모두 거주자에게 물은 폰 알림**(같은 날·같은 시각·같은 장면)만 분모로 뺐다. 그림: `figures/ab_acceptance_diff.png`.

| 거주자 모델 | 성향 | A | B | A − B (씨앗별 차이, 95%) |
|---|---|---|---|---|
| 기본(피로 0.15, 수고 0.12), 운영 학습 | 거부형 | 0.434 | 0.543 | −0.099 [−0.127, −0.074] |
| 〃 | 무시형 | 0.406 | 0.517 | −0.107 [−0.130, −0.086] |
| 〃 | 뒤바뀜형 | 0.450 | 0.502 | −0.052 [−0.081, −0.025] |
| 피로만 켬(수고 0) | 거부형·무시형·뒤바뀜형 | | | −0.018 · −0.016 · −0.018 |
| 수고만 켬(피로 0) | 거부형·무시형·뒤바뀜형 | | | −0.095 · −0.101 · −0.052 |
| **피로·수고 모두 0 (통제)** | 3종 | 0.603·0.558·0.581 | 같음 | **0.000 · 0.000 · 0.000** (구간 0~0) |

- A(모든 제안에 명시 확인)가 B(위험도별 확인)보다 수락이 5~11%p 낮게 나왔다. 그러나 이 차이는 거주자 모델이 '확인이 셀수록 덜 누른다'(수고 계수)고 가정해서 생긴 것이다. 수고만 켜도 거의 그대로, 둘 다 0 이면 정확히 0 이다. 즉 이 실험은 A·B 의 우열을 알려 주지 않고, **우열이 거주자 가정의 크기에 비례한다**는 것만 보여 준다. 통제에서 차이가 0 이므로 시뮬레이터 결함은 아니다(사전 등록의 결함 기준).
- 파급 효과: A 에서는 덜 눌러 만료가 늘고(만료 폰 알림 하루 0.30 대 0.23) 만료는 '비선호' 신호로 쌓이므로, 운영 학습에서 하루 수락된 도움 제안이 0.41(A) 대 0.71(B)로 벌어졌다(수락률만 보면 0.43 대 0.52). 작은 가정 차이가 학습 때문에 증폭된다.

### 모아보기(digest) — 따로 보고

| 변형(조건 B, 운영 학습) | 모아보기 항목 하루 1~14일 | 31~60일 | 모아보기로 수락된 도움(60일) | 수락된 도움 합계 31~60일 |
|---|---|---|---|---|
| main (22시에 80% 확률로 열람) | 0.99 | 0.82 | 0.42 | 0.72 |
| tray0 (아무도 안 열람 = 실제 데몬) | 0.33 | 0.14 | 0.00 | 0.37 |

- 실제 데몬처럼 모아보기가 전달되지 않으면 운영 학습(lr30)에서 모아보기 제안이 14일 만에 3분의 1로, 31~60일에는 하루 0.14건으로 사그라든다. 만료가 '비선호'로 쌓여 취침 준비 선호 셀이 30일째 0.41(열람하는 경우 0.65)까지 내려가기 때문이다. 이것이 `findings.md` 에 적힌 결함의 크기다. 학습이 없는 팔(none, explicit_only)은 모아보기 항목이 줄지 않고(하루 1.2건 유지) 다만 한 건도 수락되지 않고 만료된다.
- 성향 합침 표의 '수락된 도움 제안'은 모아보기 수락을 포함한다. tray0 에서는 이 값이 대부분 절반 가까이 낮다(예: none 31~60일 1.19 → 0.67).

### 안전 경로 점검

1,080회 × 60일 = 64,800건의 안전 첫 알림이 모두 즉시 전송됐다(`safety_ok_all` = true). 센서 값 입력부터 전송까지의 최댓값은 286.8 ms(기계 부하가 25~121 였던 때 포함, 기준 값이 아님).

## 가설 판정

| 가설 | 사전 등록 조건(HYPOTHESES v2) | 판정 | 근거 |
|---|---|---|---|
| H4.1 학습의 효과 (탐색) | 하루 수락된 도움 제안·잘못 꺼진 도움 제안(숨은 선호 기준)이 주 지표, 수락률은 보조 | **학습의 이득은 지지되지 않음, 게이트의 이득은 지지됨** | lr30 은 explicit_only 대비 수락된 도움 −0.13/일, 잘못 꺼진 도움 +0.38/일(구간이 0 을 포함하지 않음), 쓸데없는 알림 차이 0.00. 쓸데없는 알림 감소(−0.13/일 대 none)는 [그만해]+30일 쉬기가 낸다. |
| H4.2 = P5 선호가 바뀌면 따라가는가 | "30일 게이트가 있는 모든 변형이 회복 실패이고 게이트 없는 변형만 회복하면 '회복을 막는 것은 학습률이 아니라 30일 게이트'" | **강한 형태는 반증, 약한 형태는 지지** | 30일 쉬기 팔이 45일 안에 97% 회복(중앙 17일). 게이트는 회복을 막지 않고 약 10~12일 늦춘다. 실제로 회복을 막는 것은 영구 차단(0%)과 학습 60%(뒤바뀜형 20%). 지연의 크기는 [그만해]에서 선호 변화까지의 간격에 달렸다(아래 한계). |
| H4.3 확인 방식과 수락 (탐색, 모델 의존) | 두 조건 모두 물은 항목만 분모. 피로 계수를 0 으로 둬도 차이가 남으면 시뮬레이터 결함 | **판정 불가(거주자 가정이 결정)** | A−B = −0.05~−0.11 이지만 수고·피로 0 이면 정확히 0.000. 결함은 아님. |

## 한계

- **거주자는 가정이다.** 알아챔·지연·피로·수고·잘못 누름의 값은 모두 정한 값이며 실제 사람 자료가 아니다. 특히 H4.3 의 결과는 수고 계수 0.12 의 크기에 비례한다. 계수를 바꾸는 민감도 스윕은 하지 않았다(다음 사이클).
- 성향은 3종뿐이고 선호 변화는 15일째 한 번뿐이다. 선호가 15일째 바뀌는 것이 30일 쉬기와 어떤 간격이었는지가 지연 일수를 결정한다(여기서는 [그만해]가 1~3일째라 지연 약 17일). 간격이 짧거나 길면 달라진다.
- 반대 방향의 변화(좋아하다 싫어하게 됨)에서 학습이 없는 팔이 입는 피해는 뒤바뀜형의 절반만 본다. 별도 성향을 두지 않았다.
- 모든 팔에서 '출처별 수락률' 채널(origin accept-rate)은 켜져 있다. none 은 학습률 0·쉬기 없음일 뿐 완전히 정적인 것은 아니다.
- 회복 정의를 사전 등록 문장에서 바꿨다(위 방법). 문자 그대로의 값은 `summary.json` 의 `recovery`(성향 둘에서 의미 없음)에 남겼다.
- 씨앗은 대본의 시각·값만 바꾼다. 장면 수가 넷뿐이어서 같은 하루가 비슷하게 반복되고 성향이 3종이라 일반화에 한계가 있다.
- 구간은 씨앗 10개의 부트스트랩이다. 성향을 합친 구간은 성향을 고정 요인으로 보고 성향×씨앗 30쌍을 다시 뽑는다.
- 시간은 지표가 아니다(기계 부하가 25~121 였고, 각 기록에 `load1` 을 남겼다).
- 요약 파일(`results/summary.json`, 2 MB)은 모든 (변형·성향·팔·조건)의 구간을 담아 크다.

## 다음 사이클 제안

- **꼬리 가설**: 선호 변화 시점을 [그만해] 직후(4·8일)·쉬기 만료 직전(28일)·만료 뒤(35일)로 바꿔 게이트 지연이 0~30일에서 어떻게 변하는지 본다. 쉬는 기간(7·14·30일) 스윕을 같이 한다.
- **대안 가설**: (1) [그만해]를 한 번 누른 즉시 차단하지 않고 두 번째에 차단(오탭 방어). (2) 쉬는 중에도 거주자가 수락하면 쉬기를 푸는 규칙. (3) 모아보기 항목의 만료를 비선호로 세지 않는 규칙(`findings.md` 의 접근). (4) 수고 계수 0~0.33 스윕으로 A·B 의 판정이 어느 계수에서 뒤집히는지.
- 실제 사용자 응답 자료가 생기면 거주자 모델의 알아챔·수고 값을 그 자료에서 잰 값으로 바꾼다.
