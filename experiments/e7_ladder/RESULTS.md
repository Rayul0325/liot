# E7 — 알림 사다리 명세 적합(H6.1)과 보호자 동시·순차 호출(H6.2)

## 1. 목적

- **H6.1 (적합성 확인, 가설 수에서 제외)**: 실제 LIOT 서비스의 알림 사다리가 `docs/business-rules.md` 에 적힌 시각을 지키는가. 사전 등록 기준: "명세 대비 오차 1초 이상이 1건이라도 있으면 결함으로 보고."
- **H6.2 (탐색)**: 보호자를 한꺼번에 부르는 현재 방식(동시)과 한 명씩 90초 간격으로 부르는 대안(순차)을 비교한다. 지표는 첫 확인까지 걸린 시간과 사건당 호출받는 사람 수다.

## 2. 방법

### H6.1
- 진짜 `LiotService` 를 가짜 시계 위에서 돌렸다(`experiments/e7_ladder/scenarios.py`). 시나리오 16개: 거주자 확인 3가지 시점, 보호자 확인, 보호자 0·1·3명, 동의 철회(전달 전·후), 상황 해소, 취약 거주자 + 문 열림(경고→위험), 경고 상황, 모델만 위험으로 올림, 보호자 송신 실패 뒤 복구, 헌장 OFF, 동의 없는 보호자.
- **명세 시각은 코드의 상수가 아니라 문서에서 옮긴 숫자 그대로** 시나리오에 적었다: 첫 알림 0초 · 위험 재알림 60초마다 · 경고 재알림 600·1200·1800초 · 보호자 전달 90초(전원 같은 순간) · 119 안내 390초(전달 5분 뒤, 보호자 0명이어도) · 송신 실패 재시도 30초 · 해소는 즉시.
- 시계를 움직이는 방식 4가지로 각각 돌렸다. 시나리오 16 × 방식 4 = 64회.
  - `event`: 서비스가 저장한 다음 발화 시각으로 시계를 점프(이상적인 데몬).
  - `tick5`: 0초부터 5초 간격(실제 데몬의 사다리 해상도 5초).
  - `tick5_p1.7`, `tick5_p3.3`: 같은 5초 간격이지만 틱이 상황이 열린 순간과 어긋난 경우(위상 1.7초, 3.3초). 실제 데몬은 틱이 상황과 정렬돼 있지 않다.
- 실제 시각은 시나리오 구동기가 송신 순간에 적은 시계 값이다(서비스 내부 시각 문자열은 초 단위로 잘리므로 쓰지 않았다).

### H6.2
- 순수 시뮬레이션(`mc.py`). 가정 전부 사전 등록값: 응답 시간 지수분포 평균 1·3·10분, 무응답 확률 q = 0·20·40%, 방관 효과 b = 0·0.3·0.6(보호자 N명이면 1인 응답 확률 = (1−q)/N^b), 순차 대기 90초, 보호자 수 N = 1·2·3·5.
- 설정 108개 × 정책 2개. 설정마다 10,000회(500회씩 20 묶음). 두 정책은 **같은 난수**를 받는다. 구간은 20개 묶음을 단위로 한 부트스트랩 95%다.
- 닫힌 식(기대 시간·호출 수·300초 안 확인 확률)을 따로 계산해 시뮬레이션과 대조했다.

- 정책이 계산한 시각은 명세와 정확히 같다(event, tick5). 사건이 빠지거나 끼어든 경우도 없다. 문서화된 동작(헌장 OFF 에서도 보호자 전달이 나감, 모델 상향은 보호자·119 를 만들지 않음, 동의 철회 뒤 해당 보호자에게 아무것도 안 감, 송신 실패 시 30초 재시도)도 시나리오로 확인됐다.
- **H6.1 은 등록 문구('오차 1초 이상 1건이라도')대로 반증이다.** 실제 데몬은 사다리 틱이 5초 간격이고(`LADDER_RESOLUTION_S`) 상황이 열린 순간과 정렬되지 않으므로 모든 사다리 발화가 0~5초 늦다. 위상 1.7초면 146건 모두 1.7초, 3.3초면 3.3초 늦는다(5초 미만이 설계상 한계). 정책 계산은 명세와 정확히 같고(event·tick5 오차 0초), 어긋남은 틱 해상도에서 온다. '결함은 아니다'라고 다시 읽는 것은 사후 해석일 뿐 판정을 바꾸지 않는다. 문서의 "60초마다·90초에" 는 실제로 "60~65초, 90~95초" 다.
- **사후 변경(이미 `HYPOTHESES.md` 에 기록됨)**: 시나리오 S14 의 119 안내 기대값을 실행 뒤에 390초 → 510초로 고쳤다(명세 "그 전달 5분 뒤"). 실행 전 기대값으로는 부적합이 났고, 고친 뒤 적합이다. 모델 상향 시나리오(S13)의 재알림 분류기도 실행 뒤에 고쳤다. 서비스 동작은 바꾸지 않았다. 고치기 전 초안 결과는 보관만 하고 커밋하지 않았다.

### H6.2 동시 대 순차 (시뮬레이션 · 가정 기반)

핵심 숫자(순차 − 동시, 첫 확인까지 초, 95% 구간; 무응답 q = 0, 방관 b = 0):

| 평균 응답 | N=3 | N=5 | 사건당 호출 인원 동시 / 순차(N=3) |
|---|---|---|---|
| 1분 | +33 [32, 34] | +41 [40, 42] | 3.0 / 1.23 |
| 3분 | +59 [57, 60] | +82 [80, 84] | 3.0 / 1.83 |
| 10분 | +78 [77, 79] | +131 [128, 133] | 3.0 / 2.50 |

- 보호자가 2명 이상인 모든 설정(N=2·3·5, 평균 1·3·10분 × q × b)에서 **순차 호출이 더 느리고**(구간이 0 을 포함하는 설정 0개, 순차가 더 빠른 설정 0개), 동시 호출은 항상 N명을 부른다. 순차는 사건당 호출 인원이 적다(평균 응답 1분·N=5·b=0: 5.0 대 1.23).
- 참고: 평균 응답 1분 설정 중 N≥2 의 순차 − 동시 차이는 최소 +22.9초(N=2) · 중앙 +60초 · 최대 +147초다. 보호자가 2명뿐이고 무응답·방관이 없으면 차이가 크지 않다.
- 방관 효과(b)가 커지면 두 방식 모두 느려지고 무응답 확률(300초 안에 아무도 확인하지 않을 확률)이 오른다. 예: 평균 10분·b=0.6·N=5에서 300초 안 확인 확률은 동시 0.55, 순차 0.31 — 순차는 대기 때문에 놓침이 늘어 119 안내(전달 5분 뒤)가 먼저 나갈 가능성이 높다. 반대로 호출 인원은 순차가 적어 방관 효과 가설(ADD-6)은 "사건당 호출 수에서는 순차가 낫다"로 지지되지만, 시간에서는 반대다.
- 닫힌 식 대조: 시뮬레이션의 95% 구간 안에 닫힌 식 값이 든 설정 비율은 첫 확인 시간 93%, 호출 인원 99%, 300초 안 확인 91%. 최대 상대 오차는 각각 2.4%, 0.8%, 2.2% 다(`mc.closed_form_check`). 식과 시뮬레이션이 맞는다.

## 5. 한계

- H6.2 는 보호자 응답을 지수분포로 가정한 시뮬레이션이다. 실제 가족의 응답 분포는 측정하지 않았다. 방관 효과 지수 b 와 무응답 q 도 가정이다.
- 순차 호출은 구현하지 않고 시뮬레이션만 했다. 실제 구현에서는 보호자별 90초 대기 중 송신 실패, 재시작, 동의 철회 처리가 더 필요하다.
- H6.1 은 가짜 시계와 가짜 송신기다. 송신 지연이 사다리 틱을 밀어내는 효과(H1.3)는 여기서 다루지 않았다(E1 참고).
- 시나리오 16개는 명세의 대표 경로이고 모든 조합은 아니다(예: 보호자 수 3 + 철회 + 송신 실패 동시).
- 119 안내 시각의 기준(“전달 5분 뒤” 대 “90초 + 5분”)이 문서에서 모호한 부분이 있다. 전달이 늦어지면(S14) 119 안내도 같이 밀리는 것이 현재 동작이다(510초). 따라서 **보호자 쪽 송신 장애가 오래 가면 거주자의 119 안내가 최대 약 300초(전달 5분) 늦어질 수 있다**(S14 에서는 120초 늦음: 390 → 510초).

## 사이클 2 — C2.10 방관 효과를 '동시에 호출된 사람 수'로 계산한 순차 대 동시 호출

**등록된 가설(C2.10)**: 순차 호출은 한 번에 한 명만 부르므로 방관 효과를 N 이 아니라 동시에 호출된 수로 적용한다. 두 해석을 모두 보고한다. 예측: b ≥ 0.3 에서 순차 호출이 300초 안 확인 확률이 더 높다. 반증: b = 0.6 에서도 동시 호출이 높으면.

**방법**: 사이클 1 과 같은 108개 설정(평균 응답 1·3·10분 × 무응답 0·20·40% × b 0·0.3·0.6 × 보호자 1·2·3·5명), 설정마다 10,000회, 같은 난수. 두 해석을 나란히 쟀다. (해석 N) 두 방식 모두 보호자 수 N 으로 1인 응답 확률 (1−q)/N^b 를 계산(사이클 1). (해석 동시 호출 수) 동시 호출은 (1−q)/N^b, 순차 호출은 한 번에 한 명이라 (1−q)/1^b = 1−q. 보호자 1명 설정은 두 방식이 같아 제외하고 N ≥ 2 인 27개 설정(b 별)에서 센다. 구간이 겹치지 않을 때만 '높다'고 센다.

300초 안 확인 확률(순차 − 동시, 설정별 구간 분리로 센 설정 수 / 차이 중앙값):

| b | 해석 N: 순차가 높은 설정 | 동시가 높은 설정 | 구간 겹침 | 차이 중앙값 | 해석 동시 호출 수: 순차가 높은 설정 | 동시가 높은 설정 | 구간 겹침 | 차이 중앙값 |
|---|---|---|---|---|---|---|---|---|
| 0 | 0 | 22 | 5 | −4.3%p | 0 | 22 | 5 | −4.3%p |
| 0.3 | 0 | 24 | 3 | −6.3%p | 18 | 4 | 5 | +3.3%p |
| 0.6 | 0 | 24 | 3 | −8.0%p | 27 | 0 | 0 | +15.6%p |

- b = 0 에서는 두 해석이 같다(방관 효과가 없으니 해석 차이도 없다).
- 예: 평균 3분·무응답 20%·b = 0.6·보호자 3명에서 300초 안 확인 확률은 동시 71.3%, 순차(해석 N) 62.5%, 순차(해석 동시 호출 수) 90.9%. 평균 10분·b = 0.6·보호자 5명에서는 47.1% / 25.3% / 56.8%.
- 첫 확인까지 시간(확인된 사건)의 순차 − 동시 차이 중앙값은 해석 동시 호출 수에서 b = 0.3 에 +22초(−52~+76초), b = 0.6 에 +9초(−123~+57초)로 줄어든다(해석 N 에서는 +76초, +81초). 호출 인원은 순차가 중앙값 1.9명, 동시가 3.0명이다.

**판정(C2.10 조건대로)**: 해석 **동시 호출 수**에서는 예측이 지지된다: b = 0.6 에서 순차가 모든 27개 설정에서 높고(반증 조건 '동시 호출이 b = 0.6 에서도 높음'에 걸리지 않음), b = 0.3 은 18/27 에서 높고 4/27 에서 낮다(5/27 은 겹침) — 예측 문구 'b ≥ 0.3 에서 순차가 더 높다'는 b = 0.3 에서 대체로 맞지만 전부는 아니다. 해석 **N** 에서는 b = 0.6 에서도 동시 호출이 24/27 에서 높아 반증 조건에 걸린다. 따라서 결론은 **어느 해석을 쓰느냐에 달렸다**: 방관 효과가 '같이 호출된 사람 수'로 생기는 것이라면 순차 호출의 직렬성 자체가 방관 효과를 줄여 대기 시간의 손실을 상쇄하고, '보호자 수'로 생기는 것이라면 순차 호출은 늘 불리하다. 이것은 가정 비교이고 실제 가족의 반응은 측정하지 않았다. 닫힌 식과 시뮬레이션의 대조는 사이클 1 과 같다(구간 안 비율 93% / 99% / 91%, 최대 상대 오차 2.4%).

재현: `python -m experiments.e7_ladder.run --part mc` 후 `--analyze` (요약 `mc.c2_10`).
