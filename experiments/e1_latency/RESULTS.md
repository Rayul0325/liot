# E1 — 첫 경보 지연: 표 우선 발송 대 모델 뒤 발송, 느린 편의 판정, 느린 송신

## 1. 목적

위험 신호(가스 등)가 들어왔을 때 첫 경보가 얼마나 빨리 나가는지를, 구조를 바꿔 가며 같은 조건에서 비교한다. 사전 등록(`experiments/HYPOTHESES.md` v2)의 H1.1(구조 비교), H1.1c(2단계 불일치율), H1.2(편의 판정이 루프를 막는 문제, U1 전후), H1.3(송신 지연의 영향)을 다룬다. 비교 상대에게도 가장 유리한 설정을 주었다. LIOT 에 불리한 결과도 그대로 적는다.

## 2. 방법

모든 실험은 진짜 `LiotService`(가짜 시계 없이 실시간, 가짜 ntfy 송신기 `TimedTransport` 가 도착 순간을 기록)를 쓴다. 원자료마다 커밋 해시·부하(load1)를 적었다(수집 커밋 `868a35e`, 깨끗한 작업 트리, 기계 부하 평균 17–25 — 시간은 같은 시간대에 번갈아 잰 상대 비교로만 읽는다).

**H1.1 구조 5종 × 모델 조건 4종 (사건 300건, 칸 20개, 6,000회)**
- 구조: (a) LIOT 표 우선(운영 코드 그대로) · (b) 모델 판정 뒤 발송 · (c) 짧은 마감 대기 0.25 / 0.5 / 1.0초. (b)(c)는 운영 서비스를 상속한 얇은 래퍼(`arms.py`)이고 첫 알림 직전에 모델을 기다리는 것만 다르다. 운영 함수를 복사하지 않았다. 대안은 가장 유리한 설정이다: 모델이 예외를 내면 곧바로 보내고, 마감(서비스 2단계 마감 2초)이나 대기 시간이 지나면 기다리지 않고 표 값으로 보낸다. 늦게 온 답은 운영 코드의 2단계 경로가 그대로 처리한다.
- 모델 조건: 정상(0.2초) · 느림(1.5초) · 예외 · 마감 초과(4초). 모델 지연은 합성 상수이고 실제 모델 지연 분포가 아니다.
- 사건은 칸마다 같다(짝지은 설계): 같은 카테고리(가스·연기·누수·문·오븐·고온)와 같은 '모델이 위험으로 올릴 사건' 표시. 올림 확률 30%는 **가정**이다. 칸 순서는 사건마다 돌려 가며 번갈아 잰다(10개 프로세스로 나눠 병렬 수집).
- 지표: 첫 경보 벽시계 지연, 사건당 푸시 수, 첫 푸시의 세기와 마지막 푸시의 세기가 다른 비율.

**H1.1c 벤치 재생**: `bench/risk/raw/*.jsonl` 의 '상황' 사례 32건 × 모델 6종의 원시 답(위험도·파급도·판독 실패)을 진짜 서비스에 그대로 넣어 재생했다(시간 측정 없음, 설명 통계).

**H1.2**: 편의 판정 시간 T = 0.5 / 1.5 / 3초(이벤트 루프를 막는 방식 그대로), 판정 시작 뒤 o 초에 가스 신호 도착(o = T 의 5%·25%·50%·75%·95%). 편의 판정 없는 대조군을 같은 시간대에 번갈아 쟀다. 칸 18개 × 40회 = 720회, `--tag before`(U1 전). 도착 시각은 루프가 막혀 있어도 흔들리지 않게 별도 스레드에서 찍는다.

**H1.3**: ntfy 송신 지연 0 / 2 / 5 / 10초 × 보호자 0·1·3명. 첫 송신 중에 연기 신호가 들어오는 경우와, 90초 뒤 사다리가 재알림 + 보호자 전달을 보내는 중에 들어오는 경우(송신이 차례로 이어짐). 칸 16개 × 30회 = 480회.

## 3. 결과

### H1.1 첫 경보 지연 (그림 `figures/latency_by_arm_cond.png`)

LIOT 는 모든 조건에서 중앙값 2.6–2.7ms, p95 4.3–4.7ms(구간 포함 3.7–5.1ms)다. 아래는 LIOT 와의 차이(짝지은 차이, 부트스트랩 95% 구간, ms).

| 구조 | 모델 정상 0.2초 | 모델 느림 1.5초 | 모델 예외 | 마감 초과 4초 |
|---|---|---|---|---|
| 모델 뒤 발송, 중앙값 차이 | +205.4 [204.9, 205.8] | +1506.6 [1505.8, 1507.1] | +0.5 [0.4, 0.6] | +2002.0 [2001.9, 2002.2] |
| 모델 뒤 발송, p95 차이 | +208.9 [208.2, 209.6] | +1509.6 [1508.9, 1510.3] | +0.3 [−0.1, 1.9] | +2001.9 [2001.4, 2002.6] |
| 0.25초 대기, 중앙값 | +205.4 [204.8, 206.1] | +251.2 [251.0, 251.5] | +0.5 [0.4, 0.6] | +251.5 [251.2, 251.7] |
| 0.5초 대기, 중앙값 | +206.1 [205.5, 206.9] | +501.4 [501.2, 501.6] | +0.6 [0.5, 0.7] | +501.6 [501.4, 501.9] |
| 1.0초 대기, 중앙값 | +206.0 [205.5, 206.5] | +1001.8 [1001.6, 1002.0] | +0.7 [0.6, 0.8] | +1001.6 [1001.4, 1001.8] |

- 대안의 지연은 **모델이 정상이어도** 모델 시간(약 0.2초)만큼 더 걸리고, 느린 모델과 마감 초과에서는 기다린 시간만큼 더 걸린다. 모델이 예외를 낼 때만 차이가 사실상 없다(0.5ms 안팎).
- 이 차이는 '기다린다'는 구조 정의에서 나온 것이라, 숫자 자체는 **구조상 결과**에 가깝다. 이 합성 지연 설정에서는 대안이 지연에서 이기는 칸이 없었지만, 그것은 대안이 모델을 기다리도록 정의됐고 하한을 아는 대안(위험 하한이면 기다리지 않음)을 아직 시험하지 않았기 때문이다 — 지연에서 지는 것이 대안 일반의 성질이라는 뜻이 아니다(사이클 2 C2.7 에서 하한을 아는 대안으로 다시 쟀다). 대안의 이점은 아래 푸시 수에서 나온다.
- 짧은 마감 대기 중 대표값: 네 조건 평균 p95 가 가장 낮은 것은 0.25초(0.18초)이다(0.5초 0.31초, 1.0초 0.56초). 지연만 보면 짧을수록 유리하다는 당연한 결과다. 반대로 모델이 대기 창을 넘기는 순간(느린 모델) 짧은 창은 LIOT 와 똑같이 2단계로 후속 알림을 보낸다.
- 폰에 알림이 도착하는 데 걸리는 시간 대비 비율은 구하지 않았다(ntfy 전달 시간은 측정하지 않음).

### H1.2 느린 편의 판정이 가스 첫 알림을 늦춘다 — U1 전(before)과 후(after) (그림 `figures/h12_comfort_blocks_gas.png`)

- 가스 신호가 편의 판정 시작 o 초 뒤에 오면 지연 중앙값은 T − o 에 맞는다. 예측 대비 중앙값 오차는 +3.3~+3.6ms 이다. 3개 T × 5개 o 의 15칸 모두 중앙값 구간 폭이 2.6–5.1ms 다(예: T=1.5, o=0.075 → 1.429초 [1.428, 1.430], 예측 1.425).
- 반증 조건("지연 < (T − o) − 50ms 가 o 대부분에서")에 걸린 사례: 600건 중 0건.
- 대조군(편의 판정 없음) 지연: 중앙값 2.1–2.2ms, p95 2.8–4.3ms. o 전체에서 (가스 지연 p95) − (대조군 p95) 는 T=0.5초에서 0.480초, 1.5초에서 1.429초, 3.0초에서 2.853초이다.
- 위가 `--tag before`(수집 커밋 `868a35e`) 기준선이다.

**U1 후(after)**: U1(편의 판정을 워커 스레드로 보냄, 커밋 `7c5b658`)이 들어간 코드(수집 커밋 `a7e0af2`, `liot/app.py` 의 `asyncio.to_thread(self.judge.judge …)` 확인, `liot.__file__` 이 이 작업 트리를 가리킴)로 같은 명령을 다시 돌렸다(`--tag after`, 4개 프로세스, 칸 18개 × 40회 = 720건). 편의 판정 도중 도착한 가스 알림이 막힘 없이 나간다:

| 편의 판정 T | 가스 첫 알림 지연 중앙값(전 → 후) | 가스 p95, 도착 시점 전체(전 → 후) | 대조군 p95 (전 → 후) | (가스 p95) − (대조군 p95) 후 [95% 구간] | 사후 기준 ≤ 0.1초 |
|---|---|---|---|---|---|
| 0.5초 | 0.03–0.48초 → 5.1–5.9ms | 0.483초 → 18.2ms | 2.8ms → 12.0ms | +6.2ms [−17.2, +10.9] | 충족 |
| 1.5초 | 0.08–1.43초 → 5.1–5.6ms | 1.433초 → 17.6ms | 4.3ms → 11.1ms | +6.5ms [−3.2, +12.1] | 충족 |
| 3.0초 | 0.15–2.85초 → 5.3–5.6ms | 2.857초 → 17.8ms | 3.5ms → 12.7ms | +5.1ms [+0.3, +12.0] | 충족 |

- 도착 시점별 15칸 모두에서도 (칸 p95) − (대조군 p95) ≤ 12.5ms 이고(중앙값 구간 폭 0.6–3.0ms),, 600건 모두 편의 판정이 실제로 돌았다(`judged` 100%, 가스 누락 0건). 편의 판정을 부른 틱 자체는 여전히 약 T초 걸린다(T=1.5초 중앙값 1.512초) — 판정이 끝나기를 기다리는 순서는 그대로다(앱 설계 의도).
- **주의(공정성)**: after 수집 때 기계 부하(load1 중앙값 약 78)가 before(약 21)보다 훨씬 높았다. 그래서 대조군 p95 도 2.8–4.3ms 에서 11–13ms 로 올랐다. 판정은 같은 시간대에 번갈아 잰 대조군과의 차이로 했으므로 이 부하 차이는 결론을 바꾸지 않는다.

### H1.3 송신이 느리면 다음 안전 경보가 늦다 — 특성 기록 (그림 `figures/h13_send_delay.png`)

두 번째 안전 신호(연기)의 첫 알림 지연 중앙값(초), 사건 30회씩, 구간은 ±0.01초 안팎:

| 송신 지연 | 첫 송신 중 | 사다리 중 · 보호자 0명 | 보호자 1명 | 보호자 3명 |
|---|---|---|---|---|
| 0초 | 0.003 | 0.003 | 0.003 | 0.003 |
| 2초 | 1.911 | 1.907 | 3.914 | 5.920 |
| 5초 | 4.907 | 4.909 | 9.913 | 14.919 |
| 10초 | 9.907 | 9.910 | 19.918 | 29.925 |

- 지연은 (막힌 송신 횟수) × 송신 지연 − 0.1초(신호 도착 시점)이다. 사다리가 일할 때는 거주자 재알림 1회 + 보호자 수만큼 송신이 이어지므로, 보호자 3명·송신 10초이면 두 번째 안전 신호가 약 30초 늦는다. 첫 송신 중이면 송신 지연의 95–99%다. 가설이 아니라 특성 기록이므로 판정은 없다.

## 4. 가설 판정

| 가설 | 판정 | 근거 |
|---|---|---|
| H1.1 표 우선 대 모델 뒤 발송의 지연 차이 | **구조상 결과**('지지' 아님) | Δ 는 대안이 합성 모델 시간만큼 기다리도록 정의된 값이다(정상·느림·마감 초과 12개 칸 구간이 0 위, 예외 조건은 중앙값 차이 0.5ms·p95 차이 구간이 0 포함). 비교 결론에는 쓰지 않는다. |
| H1.1c 2단계 불일치율 | 기술 통계(판정 없음) | 합성 17.3%(가정 의존), 벤치 재생 16.7% [11.5, 21.9], 모델별 0–25% |
| H1.2 (U1 전) 지연 ≈ T − o | **재현**(판정 아님) | 이미 알려진 결함의 재현이라 반증 조건이 걸릴 수 없었다. 예측 대비 오차 +3~4ms. 판정은 U1 후 측정(아래 행)에서 낸다. |
| H1.2 (U1 후) (가스 p95) − (같은 시간대 대조군 p95) ≤ 0.1초 | **지지**(세 T 모두 충족) | 차이 +5.1~+6.5ms, 구간 상한 ≤ 12.1ms. U1 이 문제를 풀었다. |
| H1.3 송신 지연 특성 | 특성 기록 | 지연 ≈ 막힌 송신 수 × 송신 지연 |

### 탐색 한 줄: 비규약 예외 새는 문제는 U1 뒤에도 그대로인가

- 같은 재현(`RaisingBackend(RuntimeError("boom"))` + 컴포트 틱)을 U1 이 들어간 코드에서 다시 돌렸다. `run_tick` 은 여전히 `RuntimeError` 를 던지고(경로가 `app.py:446 asyncio.to_thread` → `llm_judge.py:272 judge` → 백엔드로 바뀌었을 뿐 예외는 `await` 로 그대로 올라온다), `svc.run(...)` 도 여전히 `RuntimeError` 로 끝난다. `LLMUnavailable` 은 여전히 흡수된다. U1 은 예외 처리를 더하지 않으므로 예상대로 **변화 없음**이다.

## 5. 한계

- 모델 지연(0.2·1.5·4초)·올림 확률 30%·마감 2초는 가정이다. 실제 모델의 지연 분포(벤치 `seconds` 열에 있다)와 올림 비율을 쓰면 칸별 크기가 달라진다.
- 송신기는 가짜이고 송신 지연은 `time.sleep` 이다. 폰까지 닿는 시간과 실제 ntfy 지연은 측정하지 않았다.
- 시간 측정은 한 대의 바쁜 기계(부하 17–25, H1.2 after 는 약 78)에서 번갈아 쟀다. 절대값이 아니라 상대 비교다. ms 단위 값(LIOT 2.7ms 등)은 이 기계 부하에서의 값이다.
- 대안 구현은 운영 서비스를 상속한 래퍼라 운영 함수의 부수 효과(판단 행 저장 순서 등)가 완전히 같다고 증명하지는 않았다. 판단 행 저장은 대안에서도 한다.
- H1.1c 의 벤치 재생은 상황 사례 32건(16쌍 × 2회)이고 맥락 문장이 운영과 다르다. 모델은 정답이 아니다(불일치 ≠ 오류).
- H1.3 의 신호 도착 시각은 별도 스레드가 송신 시작 0.1초 뒤로 정했다. 도착 시점을 바꾸면 지연이 그만큼 줄어든다(기울기 1).
- 수집 중 H1.3 의 지연 0 칸에서 주입 경쟁 조건으로 기록 2건이 빠졌다(스레드 콜백이 돌기 전에 대기를 끝냄). 주입 대기 코드를 고치고 그 2건만 다시 측정했다(커밋 `e2950af` 이후 수집).

## 6. 다음 사이클 제안

- 꼬리 가설: 실제 모델 지연 분포(벤치 `seconds`)를 지연으로 재생하면 짧은 마감 대기(0.25~1.0초)가 모델 답을 얼마나 잡는가.
- 대안 가설: 첫 알림은 표 값으로 즉시 보내되, 같은 상황의 후속(올림) 푸시를 짧은 창 안에서 하나로 묶는 변형은 푸시 수를 줄이는가.
- 송신을 비동기로 바꾸면 H1.3 의 기울기가 1 에서 0 으로 내려가는가(U2, 이번에는 측정만 했다).

## 사이클 2 — C2.7 하한을 아는 '모델 뒤 발송' (대안 공정화)

**등록된 가설(C2.7)**: 하한이 이미 위험(가스·연기)이면 기다리지 않고 바로 보내고, 경고 하한일 때만 모델을 기다리는 대안은 위험 하한 사건에서 LIOT 와 지연 차이 0·사건당 푸시 동일이고, 맞교환(지연 대 푸시 수)은 경고 하한 사건에서만 남는다. 반증: 위험 하한 사건에서도 차이가 남으면.

**방법**: 구조 3개 — LIOT · 항상 모델을 기다리는 대안(사이클 1 의 모델 뒤 발송) · **하한을 아는 대안**(`floor_aware`: 하한이 위험이면 운영 경로로 즉시 보내고 2단계는 그대로, 경고 하한만 모델을 기다림). 모델 지연은 합성 상수가 아니라 **벤치 실측 시간**이다: `bench/risk/raw` 상황 사례 중 답이 나온 160건(jev-omni 의 판독 실패 제외)의 판정 시간 중앙값 0.957초, p95 1.37초, 최대 1.42초에서 사건마다 하나를 뽑는다(세 구조에 같은 값). 사건 600건(위험 하한 214, 경고 하한 386)을 짝지어 쟀고 올림 30%는 이전처럼 가정이다. 수집 커밋 깨끗한 작업 트리, 8개 프로세스.

**판정(C2.7): 구조상 결과(공정화 확인) — '지지'가 아니다.** 위험 하한 사건에서 하한을 아는 대안은 LIOT 와 지연 차이의 구간이 0 을 포함하고(−0.1ms, p95 +2.4ms) 푸시 수도 같다. 그러나 이것은 코드 구성상 반드시 그렇게 된다: 하한이 위험이면 `floor_aware` 가 운영 경로(`LiotService.dispatch`)를 그대로 타기 때문이다(`arms.py` 73–74행). 따라서 이 두 예측은 시험된 것이 아니라 공정화가 올바르게 구현됐음을 확인한 것이고, 반증 조건이 걸릴 수 없었다. 정보가 있는 부분은 경고 하한의 크기뿐이며 이는 **기술 결과**다(아래, 올림 30% 가정에 기댐). 기술 결과(올림 30% 가정 조건부): 경고 하한 사건에서 대안은 약 1초(벤치 모델 시간) 늦게 보내는 대신 푸시를 한 번으로 줄이고(26.7% 건에서 두 번째 푸시가 사라짐) 첫 경보의 세기가 곧 최종 세기다. 사이클 1 의 H1.1 이 대안의 지연 불이익을 과대하게 보여 준 것은 위험 하한 사건을 기다리게 만든 대안 탓이었고, 하한을 알게 하면 그 불이익은 경고 하한 사건에만 남는다. (올림 확률 30% 가정과 합성 사건 구성에 의존하므로 경고 하한 칸의 푸시 수 차이 크기는 가정 의존이다. 운영 모델의 실제 올림은 E5 에서 61문항 중 0–2건이라 현재 운영에서는 이 차이가 더 작다.)
