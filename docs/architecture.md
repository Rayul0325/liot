# 시스템 구성

## 전체 그림

liot 는 집 하나에 프로세스 하나로 도는 Python asyncio 데몬이다. 두뇌(`LiotApp`)는 네트워크와 DB 를 모르고 결정만 한다. 몸통(`LiotService`)이 그 결정을 DB·알림·사다리·피드백 수신구에 잇는다. 관제실 웹 서버는 별도 프로세스이고, 데몬과 같은 SQLite 파일을 함께 쓴다.

```
        Home Assistant ──(WebSocket, 읽기만)──▶ ┌──────────── liot-serve (데몬 프로세스) ─────────────┐
                                               │ L1 HABridge → StateCache                            │
                                               │      │ (L1→L2)                                      │
                                               │ L2 ContextBuilder / 능동 생성기·아비터               │
                                               │      │ (L2→L3)                                      │
                                               │ L3 Gate1 Guardrail ─▶ Gate2 LLMJudge ─(HTTP)─▶ llama.cpp / ollama
                                               │      │ (L3→L4)                (egress LLM 정제 뒤)    │
                                               │ L4 RiskRouter → Proposal                             │
                                               │ ──────────────── LiotService ────────────────────── │
                                               │  상황 에피소드 · 표 우선 2단계 발송 · 사다리 루프     │
                                               │  Notifier 게이트 → egress NTFY 정제 → NtfyTransport ─(HTTPS)─▶ ntfy ─▶ 거주자·보호자 폰
                                               │  피드백 수신구 GET /feedback · /guardian-ack  ◀─(폰의 버튼)── │
                                               └──────────────────────┬──────────────────────────────┘
                                                                      │ aiosqlite (같은 파일, WAL)
   브라우저(이 기기) ──HTTP──▶ liot.demo_server(관제실) ───────────── SQLite (liot.db)
```

- 레이어 사이 이동은 인-프로세스 이벤트 버스로만 한다. 허용 엣지는 L1→L2, L2→L3, L3→L4, L4→L2 넷이고, 그 밖의 발행은 런타임 예외다.
- 외부로 나가는 모든 것(LLM·결정 모델 프롬프트, ntfy 알림, 기상 조회)은 egress 게이트 한 함수를 지난다. 게이트는 목적지별로 정제(LLM 은 가명화, NTFY 는 허용 키만, 기상은 좌표 격자화)하고 PII 패턴이 남으면 송신을 거부한다.
- HA 로는 읽기만 한다. 쓰기(`call_service`)는 실행 옵트인이 켜졌을 때 실행기만 부른다. 기본 데몬은 액추에이터를 부르지 않는다.

## 모듈 지도

| 모듈 | 역할 | 의존 방향 |
|---|---|---|
| `liot/core` | 위험도(RiskTier)·파급도(SeverityLevel) 값, pydantic 계약, 불변식 검사기, 이벤트 버스, egress 게이트, 테넌트 스코프, 시계 | 아무 레이어도 런타임에 임포트하지 않는다. 불변식 검사기만 L4 를 지연 임포트해 정적 검사를 한다 |
| `liot/db` | 기준 스키마, 전진 전용 마이그레이션(현재 버전 3), 안전 저장소(거주자·보호자·동의·상황·사다리·전달·판단) | core 만 쓴다 |
| `liot/layers/l1_sensing` | HA WebSocket 브리지, 값 정규화, 엔티티별 최신값 캐시 | core 만 쓴다 |
| `liot/layers/l2_context` | 맥락 스냅샷, 능동 규칙·후보·2갈래 제안·아비터, 선호 임베딩, 자연어 지시 | core 와 L4 의 기기 카탈로그(데이터)만 쓴다 |
| `liot/layers/l3_judgment` | Gate1 결정론 가드레일, Gate2 판정기, 결정 모델(llama.cpp)·ollama 백엔드 | core 만 쓴다 |
| `liot/layers/l4_execution` | 판단→제안 라우터, 개입 정책 A/B, 알림 게이트, ntfy 전송, 사다리 정책, 피드백 서명 검증, 제안 수명주기, 실행기 | core 만 쓴다 |
| `liot/app.py` | 레이어를 버스에 배선하는 두뇌. 센서 읽기·능동 틱을 판단과 제안으로 바꾼다 | 모든 레이어 |
| `liot/service.py` | 몸통. 영속·발송·상황·사다리·피드백·만료·개인화 루프 | app·db·레이어 |
| `liot/serve.py` | 데몬 진입점(`liot-serve`). 환경변수로 구성 | service |
| `liot/demo_server.py` + `web/` | 관제실 웹: 파이프라인 실험실과 안전 설정 화면 | app·db·registry |
| `liot/registry.py` | 관제실 실험실 전용 런타임 등록(센서·기기·행동·규칙, 메모리) | core·레이어 |
| `config/` | 기기 카탈로그, Gate1 규칙, 파급도 표, 능동 규칙(데이터) | 로더들이 읽는다 |
| `bench/risk` | 결정 모델 후보 측정(운영 코드 경로 재사용) | 운영 코드를 읽기만 한다 |

## 대표 흐름 1 — 가스 누출(안전 상황)

1. HA 가 `state_changed` 를 보낸다. 브리지가 상태 문자열을 정규화한다(`on`·`detected` → 참). 카테고리는 데몬 시작 때 `get_states` 로 만든 (domain, device_class) 맵에서 찾는다.
2. 서비스가 이상·정상을 가린다. 판정은 파급도 설정의 카테고리별 규칙 하나뿐이다.
3. 이상이고 열린 상황이 없으면 (집, 카테고리, 엔티티) 에피소드를 연다(`situations`). 거주자 취약 여부는 DB 에서 불리언 하나로만 읽어 표에 넣는다. 표가 하한(`severity_floor`)과 출처를 낸다.
4. 앱이 Gate1 하한과 파급도 하한만으로 1단계 판단과 제안을 만든다. 모델을 부르지 않는다.
5. 서비스가 제안을 저장하고, 알림 게이트를 통과시킨 뒤 egress 로 정제해 ntfy 로 **즉시** 보낸다. 1단계 판단 행을 저장하고 사다리를 무장한다.
6. 2단계 판정은 추적되는 백그라운드 태스크가 별도 스레드에서 돌린다(전체 마감 = 요청당 제한시간 × 4). 결과 판단 행은 늘 저장한다. 모델이 위험도나 파급도를 올렸고 상황이 아직 같은 에피소드로 열려 있으면, 같은 상황 id 의 후속 제안을 보내고 재알림 주기를 다시 잡는다.
7. 사다리 루프(5초 해상도, 300초 틱과 별개)가 DB 의 다음 발화 시각을 보고 재알림 → 보호자 전달 → 119 안내를 낸다.
8. 거주자가 버튼을 누르거나 보호자가 확인 링크를 누르면 피드백 수신구가 서명을 검증하고 사다리를 멈춘다. 센서가 정상으로 돌아오면 에피소드를 닫고, 그 상황의 대기 제안을 만료시키고, 거주자에게 '해소됨'을 보내고, 전달받은 보호자에게도 '해소됨'을 보낸다.

## 대표 흐름 2 — 능동 컴포트 틱

300초마다 서비스가 만료 스윕·1회용 토큰 스윕·거절 이력 주입·선호 셀 로드를 한 뒤 앱 틱을 부른다. 앱은 트리거 감지 → 규칙 후보 + 두 제안 라인 후보 + 무행동 → 아비터(가중합) → Gate1 → Gate2(동기) → 라우터 순서로 제안 하나를 만들거나 침묵한다. 능동 제안은 숨결(BREATH)을 넘으면 표출하지 않는다. 서비스가 후보 평가와 판단 행을 저장하고 발송한다. 알림 응답(수락·거절·만료)은 선호 셀맵을 갱신해 다음 틱의 선택에 반영된다.

## 경계에서 넘는 것과 넘지 않는 것

| 경계 | 넘는 것 | 넘지 않는 것 |
|---|---|---|
| 데몬 → ntfy | 위험도 라벨·글리프·제안 id·서명 딥링크·토픽·파급도 라벨, 상황 요약의 상황 종류 라벨·집 별칭·시각 | 기기 id·이름, 방, 판단 근거 문장, 거주자 특성, 상황 id 원문(보호자 확인 링크 안의 서명 대상 제외) |
| 데몬 → 결정 모델·ollama | 집계 요약 문자열, 시간대, 후보 행동(기기 id 는 가명 토큰), Gate1 하한 이름 | 거주자 특성, 실제 entity_id(남아 있으면 송신 거부), 자유 문자열 파라미터 |
| 관제실 → DB | 거주자 별칭·특성 답·입력자, 집 별칭·혼자 거주, 보호자·동의 | 생년월일·진단명(받을 칸이 없다) |
| 브라우저 → 관제실 안전 API | 이 기기(루프백)에서 온 요청만 | 다른 기기·다른 출처의 요청 |

## 외부 시스템

| 시스템 | 방식 | 없을 때 |
|---|---|---|
| Home Assistant | WebSocket(`auth` → `get_states` → `subscribe_events`) | 센서 스트림 없이 능동 틱만 돈다 |
| ntfy | HTTP POST `<서버>/<토픽>`, 헤더로 우선순위·버튼 | 정제까지만 하고 보내지 않는다(sanitize-only) |
| llama.cpp 서버 | HTTP `/tokenize` → `/completion` (`LIOT_LLM_BACKEND=decision`) | 판정이 degraded 로 떨어지고 하한 그대로 간다 |
| ollama | HTTP `/api/generate` (`LIOT_LLM_BACKEND=ollama` 등) | 같다 |
| SQLite | 로컬 파일, WAL, 데몬은 synchronous=FULL | — |
