# 실무 지식

각 항목은 증상 → 원인 → 대응 순서다.

## 테스트·검증

### 워크트리에서 돌린 테스트가 메인 체크아웃 코드를 검사한다

- 증상: git 워크트리에서 코드를 고치고 `make check` 를 돌렸는데, 고친 내용과 무관하게 통과하거나 실패한다.
- 원인: `.venv` 에 `liot` 이 `/Users/rayul/liot` 을 가리키는 editable 설치로 들어 있다. 워크트리에서 돌려도 `import liot` 은 메인 체크아웃을 읽는다. pre-push 훅도 같은 이유로 '푸시되는 커밋'이 아니라 '현재 트리'를 검사한다.
- 대응: 워크트리 루트에서 `PYTHONPATH=$PWD make check VENV=/Users/rayul/liot/.venv`. 확인: `.venv/bin/python -c "import liot; print(liot.__file__)"` 가 워크트리 경로를 찍어야 한다.

### 2단계 판정이 테스트 사이로 샌다

- 증상: 상황 알림 테스트가 간헐적으로 실패하거나, 테스트가 끝난 뒤 `ProgrammingError`(닫힌 DB) 로그가 찍힌다.
- 원인: 결정 모델 판정(2단계)은 `handle_reading` 이 돌아온 뒤에도 백그라운드 태스크로 돈다. 잠자기로 기다리면 타이밍에 따라 결과가 갈리고, DB 를 먼저 닫으면 태스크가 닫힌 연결에 판단 행을 쓰다 실패한다.
- 대응: 2단계가 끼는 테스트는 단정 전에 `await svc.drain_phase2()` 를 부르고, `db.close()` 전에도 부른다. 데몬 종료 경로(`run` 의 finally)도 같은 drain 을 마감+1초 제한으로 한다.

### 허용 키·필드 집합 테스트가 깨진다

- 증상: 알림 페이로드에 키를 하나 더했더니 계약·egress 테스트 여러 개가 빨개진다.
- 원인: NTFY 허용 키, 거주자 알림 필드, 보호자 알림 필드가 '정확히 이 집합'으로 고정돼 있다. 의도적인 설계다 — 새 키는 리뷰를 거쳐야 한다.
- 대응: 기기·방·근거·특성이 아닌지 확인한 뒤 세 테스트의 기대 집합을 함께 고친다. 허용 키를 넓히는 대신 기존 키에 담을 수 있는지 먼저 본다(보호자 확인 링크는 새 키 대신 기존 `signed_deeplink` 키로 옮겨 싣는다).

### 가드를 지워도 테스트가 초록이다

- 증상: 우회 분기나 상수를 지웠는데 전체 스위트가 통과한다.
- 원인: 그 가드를 직접 고정한 테스트가 없거나, 테스트가 코드 상수를 그대로 가져와 비교한다.
- 대응: 가드마다 리터럴 기대값 테스트를 두고, 가드를 지웠을 때 그 테스트 하나만 실패하는지 직접 확인한다. 예: 탭 한 번 예외는 쌍마다 별도 테스트라 한 쌍을 빼면 그 쌍의 테스트만 빨개진다.

### 시간대 버킷은 집 시간대, 테스트 기본은 UTC 다

- 증상: 데몬에서 한국 아침 7시가 '밤'(야간 정숙)으로 판정되고, 능동 예산의 '하루'가 한국 오전 9시(UTC 자정)에 넘어간다. 테스트에서는 '야간' 을 만들려면 UTC 23시를 넣어야 한다.
- 원인: `Clock.time_bucket` 은 시계의 시간대 시(hour)로 morning(06–11)·day(11–17)·evening(17–22)·night 를 정한다. `Clock(tz=None)` 이면 UTC 다. 예전 데몬은 `Clock()` 이라 UTC 로 돌았다. 능동 예산(`ProactiveState`)의 날짜 묶음도 같은 시계의 지역 날짜(`Clock.local_dt`)를 쓴다.
- 대응: 데몬 진입점(`liot/serve.py`)은 `LIOT_HOME_TZ`(기본 `Asia/Seoul`)로 `Clock(tz=...)` 를 만든다. 모르는 이름이면 기동이 한국어 `ValueError` 로 멈춘다. 테스트·관제실 실험실은 `tz` 를 주지 않아 UTC 그대로다 — 고정 시각은 UTC 로 생각해 넣는다(공용 픽스처 `night_clock` 은 UTC 23:30). 타임스탬프(`now_utc`·`now_dt`)는 시간대와 무관하게 늘 UTC 다. 확인: `Clock(fixed="2026-06-01T22:30:00+00:00", tz="Asia/Seoul").time_bucket() == "morning"`.

## 파급도·상황

### 정규화가 정수 0 을 0.0 으로 바꾼다

- 증상: 0/1 로 보고하는 불리언 센서가 정상(0)을 보내도 상황이 닫히지 않을 것처럼 보인다.
- 원인: 정규화기는 `int` 를 `float` 로 바꾼다. 이상 규칙은 `False` 와 숫자 0(0.0 포함)만 정상으로 본다. `0 is False` 같은 비교로 바꾸면 0.0 이 이상이 된다.
- 대응: 불리언 이상 규칙은 '값이 `False` 이거나, bool 이 아닌 숫자이면서 0' 일 때만 정상이다. `"unavailable"`·`"unknown"` 은 이상도 정상도 아닌 '판정 보류'다. 그 밖(1.0, 2.0, `None`, 빈 문자열, 깨진 문자열, NaN)은 이상이다. 이 판정을 다른 곳에 복제하지 말고 파급도 표의 판정 함수 하나만 쓴다.

### HA 의 `unavailable`·`unknown` 은 판정 보류다

- 증상: HA 를 재시작하면 가스 센서가 잠시 `unavailable` 이 되는데, 상황도 사다리도 열리지 않고 거주자에게 "가스 센서 · 감시 불가(연결 끊김)" 알림 한 건만 간다.
- 원인: 정규화기는 이 두 문자열을 그대로 남긴다. 파급도 판정은 이 두 값을 '보류'로 돌려주고(`is_unmonitorable`), 서비스는 이상/정상 분기 **앞에서** 보류를 처리한다. 보류 신호는 `abnormal=False` 라서, 분기 순서가 바뀌면 정상 처리로 흘러가 열린 위험 상황을 닫아 버린다.
- 대응: 신호를 새로 다루는 코드는 `abnormal` 만 보지 말고 `unmonitorable` 을 먼저 본다. 확인 방법: '열린 상황 중 보류' 테스트(`test_open_situation_stays_open_and_ladder_unchanged`)가 통과해야 한다. 감시 불가 알림의 '보냄' 표식은 메모리에만 있어 데몬을 다시 띄우면 지워진다.

### 파급도 표가 깨지면 모든 안전 신호가 '위험'이 된다

- 증상: 문 열림마다 보호자에게 전달된다. 고온 센서는 평상시 온도(예: 22.0)에도 상황을 연다.
- 원인: `situations.yaml` 을 읽지 못하거나 형식이 틀리면 표는 fail-closed 로 바뀐다: 모든 안전 카테고리가 위험이고, 카테고리별 임계(고온 55℃)도 사라져 불리언 규칙(0 이 아닌 숫자 = 이상)을 쓴다.
- 대응: 표를 고친 뒤 `make check`(칸마다 고정 테스트)와, 데몬 기동 직후 `audit_log` 에 `severity_table_load_failed` 가 없는지 확인한다. 실패 감사는 기동당 한 번만 남는다.

### 파급도 설정을 `config/rules/` 에 두면 조용히 깨진다

- 증상: 파일을 옮긴 뒤 테스트는 대부분 통과하는데 모든 상황이 '위험'이 되고 판단의 규칙셋 버전이 바뀐다.
- 원인: Gate1 로더는 그 폴더의 모든 YAML 을 합친다. `rules` 키가 없는 파일은 빈 규칙셋으로 들어가 버전 문자열에 `situations:1` 이 붙고, 파급도 로더는 원래 경로에서 파일을 못 찾아 fail-closed 가 된다.
- 대응: 파급도 설정은 `config/severity/` 에만 둔다. 확인: `load_rulesets().ruleset_version` 이 `emergency:1.0.0+night_quiet:1.0.0` 이어야 한다.

### HA 에 나중에 추가한 안전 센서는 다음 재연결까지 침묵한다

- 증상: 데몬이 도는 중에 HA 에 가스 센서를 새로 붙였더니 가스 감지에도 알림이 없다.
- 원인: 카테고리 맵은 연결(최초·재연결)마다 `get_states` 로 다시 만든다. 연결이 유지되는 동안에는 새 엔티티가 맵에 없다 — 도메인 접두사(`binary_sensor`)로 분류돼 비안전이 되고 비안전 신호는 침묵한다.
- 대응: 센서를 추가·교체한 뒤 HA 쪽 연결을 한 번 끊거나(HA 재시작 포함) 데몬을 다시 시작하면 다음 세션의 재동기화가 맵에 넣고 현재값을 흘린다. 확인: 로그의 `HA resync: N entities mapped` 수가 늘었는지 본다. `entity_registry_updated` 구독으로 즉시 분류하는 것은 하지 않았다.

## HA 연결(결정 0014)

### HA 가 끊겼는데 알림이 안 온다 / 끊기면 사다리까지 멈춘다

- 증상: HA 를 재시작하거나 네트워크가 끊겼는데 거주자에게 아무 알림이 없고, 예전에는 데몬이 끝나면서 열린 위험 상황의 재알림·보호자 전달·119 안내까지 멈췄다.
- 원인: 웹소켓 종료 예외가 스트림 밖으로 올라와 `run` 의 gather 가 사다리·틱 태스크를 함께 취소했다. 형식 오류로 스트림이 조용히 끝나는 경우는 프로세스가 살아 센서만 안 읽었다.
- 대응: `run(ha_factory=...)` 의 감독이 사다리·틱과 별개 태스크로 HA 를 재연결한다(대기 1→60초, 5분 안정 뒤에만 1초로 복귀). 끊김이 120초에 이르면(연속·10분 누적·시작 후 첫 연결 실패) 거주자에게만 '감시 중단' 한 번, 복구되면 '감시 재개' 한 번. `run(bridge)` 는 예전처럼 한 번 소비하고 돌아온다 — 감독을 쓰려면 `ha_factory` 를 넘긴다. 로그: `HA connection lost (<원인>) — retrying in N s`.
- 확인: `tests/test_ha_reconnect.py`(루프백 소켓으로 닫았다 다시 열기, 가짜 시계로 120초 경계).

### get_states 와 구독 사이에서 안전 이벤트가 사라진다

- 증상: 재연결 직후 가스가 켜졌는데 알림이 없다(스냅샷에는 아직 꺼짐, 이벤트는 구독 전이라 못 받음).
- 원인: 예전 `_request` 는 응답을 기다리는 동안 끼어든 이벤트를 버렸고, 순서도 `get_states` 가 구독보다 앞이었다.
- 대응: 세션 순서는 **구독 → `get_states` → 재동기화 → 버퍼 비우기 → 스트림**이다. `_request` 는 끼어든 `event` 를 `_pending` 에 쌓고 `next_reading`/`stream` 이 그것부터 낸다. 순서를 바꾸거나 버퍼를 지우면 `test_event_between_snapshot_and_subscribe_is_not_lost` 가 실패한다.

### HA 를 막 재시작하면 재동기화가 거짓 알림을 낸다

- 증상: HA 재시작 직후 재동기화로 모든 안전 센서에 '감시 불가' 알림이 쏟아지거나, 열린 상황이 거짓으로 닫힌다.
- 원인: 재시작 직후 `get_states` 는 `unavailable`·`attributes.restored: true` 자리표시자(디스크에서 되살린 가짜 상태)를 돌려주고, 이 자리표시자에는 `device_class` 도 없어 카테고리가 도메인 접두사(비안전)로 떨어진다.
- 대응: 재동기화 전에 `get_config` 의 `state` 가 `RUNNING` 이 될 때까지 기다린다(5초 간격·상한 5분, 넘기면 경고 뒤 진행; 필드가 없으면 기다리지 않음). 기다리는 동안 스트림은 받고 카테고리 맵만 먼저 채운다. `restored` 자리표시자는 값을 흘리지 않고, 카테고리 맵은 교체가 아니라 병합이라 자리표시자·부분 스냅샷이 이미 아는 안전 분류를 덮지 못한다. 외부 HA 동작이라 근거는 HA 문서의 표기이고, 시험은 가짜 연결로 두 경우를 고정한다.

### 재동기화가 같은 알림을 다시 내거나, 실패한 신호를 놓친다

- 증상: 재연결마다 같은 가스 알림이 반복되거나, 처리 중 예외가 난 안전 신호가 영영 사라진다.
- 원인: 재동기화는 현재값을 `handle_reading` 에 다시 흘린다. HA 는 상태 변화만 보내므로 실패한 신호는 다시 오지 않는다.
- 대응: 이 프로세스가 **성공적으로** 흘린 마지막 값(`_ha_last_fed`)과 같은 엔티티는 재동기화가 건너뛴다. 처리에 실패한 엔티티는 그 기록에서 지우고, 안전 신호였으면 재동기화를 한 번 예약한다. 재동기화 도중의 실패는 재예약하지 않는다(영구 장애에서 쉬지 않고 도는 것을 막는다).

### 실행기가 스트림과 같은 소켓을 쓰면 동시 recv 로 터진다

- 증상: 실행이 켜진 데몬에서 승인 직후 호출이 `ConcurrencyError` 로 실패하거나 스트림이 깨진다.
- 원인: websockets 는 같은 연결에서 `recv()` 를 동시에 부르는 것을 허용하지 않는다. 예전에는 시작 때 연 브리지 하나를 스트림과 실행기가 함께 썼다.
- 대응: 실행기는 호출(과 이전 상태 조회)마다 연결 팩토리로 새 연결을 열고(열기 → 인증 → 호출 → 닫기) 끝나면 닫는다(`call_service_once`/`get_state_once`). HA 에 닿지 못하면 `ExecutionError` — 서비스는 실행 실패(조작 안 함)로 받는다.

### SIGTERM 으로 끈 데몬이 DB 를 닫지 못한다

- 증상: launchd 로 끈(SIGTERM) 뒤 DB 의 마지막 쓰기가 닫히지 않는다. HA 가 꺼진 채 시작하면 프로세스가 끝나지 않고 멈춰 남는다.
- 원인: 처리기가 없으면 SIGTERM 은 `finally` 없이 프로세스를 죽인다. 예전 `serve` 는 DB 를 연 뒤 HA 호출이 `try` 밖에 있어, 실패해도 aiosqlite 의 비데몬 스레드가 닫히지 않았다.
- 대응: DB 를 연 직후부터 끝까지 하나의 `try/finally`(수신구 닫기 → DB 닫기). `_StopSignals` 가 SIGTERM·SIGINT 에 주 태스크를 **한 번만** 취소하고(정리 중 두 번째 신호는 무시) 종료 코드 0 으로 끝난다. 확인: 실제 프로세스에 `kill -TERM`·`kill -INT` 후 5초 안에 종료.

## 결정 모델

### 제한시간은 요청 하나당이다

- 증상: `LIOT_DECISION_TIMEOUT=1.5` 인데 2단계 판정이 6초 가까이 걸린 뒤에야 degraded 로 떨어진다.
- 원인: 이 값은 HTTP 요청 하나의 제한시간이다. 판정 하나는 질문 둘 × (tokenize + completion) = 최대 4 요청이다. 서비스의 2단계 전체 마감 기본값은 그 4배(1.5초면 6초)다.
- 대응: 전체 마감을 따로 정하려면 `LiotService(phase2_deadline_s=...)` 를 쓴다. 첫 알림은 이 마감과 무관하게 이미 나가 있다.

### 마감을 넘긴 판정 스레드는 끝까지 돈다

- 증상: 2단계가 마감으로 degraded 처리된 뒤에도 모델 서버에 요청이 들어온다.
- 원인: 판정은 `asyncio.to_thread` 로 돈다. `wait_for` 가 마감에서 포기해도 스레드는 취소되지 않고, 요청당 제한시간까지 HTTP 를 붙잡는다.
- 대응: 요청당 제한시간을 짧게 유지한다. 모델 서버가 멈췄으면 스레드가 기본 실행기 스레드를 붙잡으므로, 연달아 터지는 안전 상황마다 스레드가 하나씩 쌓인다.

### ollama 의 qwen3.5 는 항상 비가용이다

- 증상: `LIOT_LLM_BACKEND=ollama`, `LIOT_OLLAMA_MODEL` 에 qwen3.5 를 넣으면 모든 판정이 `degraded_fail_safe` 다.
- 원인: qwen3.5 는 ollama 에서 JSON 을 `thinking` 필드에 넣고 `response` 를 비운다. 요청에 `"think": false` 를 넣어야 하는데 ollama 백엔드는 넣지 않는다.
- 대응: ollama 백엔드에는 gemma 계열(기본 `gemma4:e4b`)을 쓴다. 결정 모델은 llama.cpp 백엔드(`decision`)로 붙인다. 수정 여부는 미결이다.

### 모델이 보는 기기 이름은 `PERSON_1` 이다

- 증상: 모델 입력 로그를 보면 `"device": "PERSON_1"` 이다.
- 원인: egress 가명화는 키 이름으로 종류를 정하는데, `device` 키는 사람 계열(PERSON) 접두사를 받는다. 의도된 가명화지만 기기를 사람처럼 부르는 토큰이라 판단을 흔들 수 있다.
- 대응: 바꾸려면 egress 가명 규칙과 벤치를 함께 다시 돌려야 한다(가명 토큰 이름이 모델 입력이므로 재현 키가 달라진다).

### 운영 모델 입력에는 자유 텍스트가 없다

- 증상: 벤치에서는 모델이 맥락 문장을 보고 파급도를 올리는데, 운영에서는 올리는 일이 드물다.
- 원인: 운영 경로의 맥락 요약은 `"[day] 1 signals; changed=1; safety=gas; trigger=sensor_reading"` 같은 집계 템플릿뿐이다. 벤치는 같은 자리에 한국어 상황 문장을 넣는다.
- 대응: 벤치 결과를 운영 성능으로 읽지 않는다. 맥락 문장을 모델에 넣으려면 그 문장의 출처·가명화·주입 방어를 먼저 설계해야 한다.

### 결정 모델 프롬프트를 고쳐도 재현 키가 안 바뀐다

- 증상: 결정 모델의 질문 문구를 바꿨는데 판단 행의 `bundle_id` 가 그대로다.
- 원인: `bundle_id` 는 프롬프트 레지스트리의 기본 판정 프롬프트 + 규칙셋 버전 + 모델 id 로 만든다. 결정 백엔드·ollama 백엔드의 실제 프롬프트 상수는 여기 들어가지 않는다.
- 대응: 프롬프트를 바꿀 때는 `LIOT_DECISION_MODEL` 값(모델 id 에 들어간다)을 함께 바꿔 구분하거나, 레지스트리 반영을 같이 고친다.

### 프롬프트 형식은 ChatML 고정이다

- 증상: 다른 계열 GGUF 를 끼웠더니 거의 모든 판정이 '선택지 글자 없음'으로 degraded 다.
- 원인: 결정 백엔드는 `<|im_start|>` ChatML 턴과 빈 `<think>` 블록을 고정으로 쓰고, 첫 토큰 top-40 에서 A–D 글자만 읽는다. Gemma 계열(Jev-Omni)은 턴 표식이 달라 글자를 내지 않았다(벤치 판독 오류 98/122).
- 대응: 모델을 바꾸기 전에 벤치로 '첫 토큰 글자 질량'과 판독 오류 수를 먼저 본다. `LIOT_DECISION_MODEL` 은 기록용 이름일 뿐 서버의 실제 모델을 검증하지 않는다 — 서버에 올린 파일과 이름을 맞춘다.

## 알림·사다리·링크

### ntfy 송신이 이벤트 루프를 막는다

- 증상: ntfy 서버가 느리거나 닿지 않을 때 다음 센서 신호 처리도 같이 늦어진다.
- 원인: transport 는 동기 urllib 호출이고 서비스는 이벤트 루프 안에서 바로 부른다. 송신 하나가 최대 `LIOT_NTFY_TIMEOUT`(기본 10초) 동안 루프를 붙잡고, 보호자 전달은 보호자 수만큼 이어 붙는다.
- 대응: 제한시간을 짧게 둔다. 비동기 transport 로 바꿀 때는 이중 확인 표식을 발급 전에 세우는 순서(발급과 표식 사이에 스윕이 끼지 않게)를 유지한다.

### 재시작하면 거주자 버튼이 전부 403 이 된다

- 증상: 데몬을 다시 시작한 뒤 이전 알림의 수락·거절 버튼을 누르면 `stale or already-used link`.
- 원인: 1회용 nonce, 이중 확인 대기 표식, 되돌리기용 이전 상태는 메모리에만 있다.
- 대응: 의도된 fail-closed 다. 열린 위험·경고 상황은 사다리가 재무장되고, 다음 재알림이 새 nonce 를 실어 보낸다. 경고 상황의 재알림 3회가 이미 끝났으면 거주자가 버튼으로 멈출 방법이 없고, 센서 정상 복귀로만 닫힌다. 보호자 확인 링크는 nonce 가 없어 재시작 뒤에도 통한다(서명 키가 같을 때).

### 프로세스가 죽으면 열린 상황이 침묵하거나 사다리 없이 남는다

- 증상: 가스 신호 한 건(DB 문장 24개)을 처리하다 프로세스가 죽으면(SIGKILL·메모리 부족·정전) 두 가지 틈이 생긴다. 창 1 — 상황 행은 커밋됐는데 첫 알림이 안 나간 채 재시작하면 푸시도 사다리도 없고(문장 5~11, 취약 거주자 집은 4~10), 같은 센서의 이상 신호는 '열린 상황 이어감'으로 삼켜져 센서가 정상이 될 때까지 700초가 지나도 푸시가 0건이다. 창 2 — 첫 알림은 나갔는데 사다리 행이 서기 전에 죽으면(문장 12~24, 취약 거주자 집 11~23) 재시작 뒤 사다리가 없어 60초 재알림·90초 보호자 전달·119 안내가 사라진다.
- 원인: 상황 행 커밋(`open_or_get_situation`)과 첫 알림 송신·사다리 생성(`_arm_ladder`)이 서로 다른 트랜잭션이다. 예외용 가드(`except BaseException: close_situation`)는 프로세스가 통째로 죽으면 돌지 못한다. `_rearm_ladders` 는 이미 있는 사다리만 돌고, 사다리는 첫 송신 뒤에야 세워진다. HA 는 상태 변화만 보낸다(`state_changed` 구독) — 그래서 상황만 닫는 복구는 센서가 이상인 채 조용하면 다음 신호가 영영 오지 않아 침묵을 보장하지 못한다. (재동기화가 연결마다 현재값을 다시 흘리지만, 그것은 HA 가 보고하는 센서에만 닿고 이미 흘린 값은 건너뛰므로 상황 행의 복구는 여전히 이 경로가 맡는다.)
- 대응: `start()` 가 사다리를 다시 무장하기 **전에** `_recover_open_situations` 로 이 집의 열린 상황 중 사다리 없는 것을 복구한다(`_recover_situation`). 제안이 저장돼 있으면 U5 의 재송신 경로(`_first_alert_unsent` → `_resend_first_alert`, 헌장 OFF·음소거·최근 거절은 그대로 침묵)로 첫 알림을 보내고, 제안이 없으면(저장 전에 죽음) 상황 행(분류·엔티티·하한)에서 첫 알림을 다시 만들어 보낸다(`_rebuild_first_alert`: 읽기값은 영속하지 않으므로 '이상, 값 모름' 불리언 True, 결정 모델은 돌리지 않고, 하한은 저장값과 지금 값 중 높은 쪽). 이미 알림이 나갔으면 다시 보내지 않고 사다리만 세운다. 마지막은 항상 `_arm_ladder` — 송신이 실패했으면 30초 재시도가 그 안에서 잡히고 모든 시각은 상황이 열린 때 기준이다(단 (a)·(b) 가 첫 알림을 지금 처음 보냈고 상황이 90초보다 오래 열려 있었으면 기준이 복구 시각이다 — 아래 '오래 묵은 고아 …' 항목). 같은 복구가 '열린 상황 이어감' 분기에서도 돈다(사다리 없고 알림 없는 상황에 이상 신호가 오면 삼키지 않는다). 이 프로세스가 지금 여는 중인 상황은 `_opening` 으로 걸러, 같은 센서의 두 번째 신호가 열던 상황을 고아로 오인해 첫 알림을 두 번 보내지 않는다.
- 남는 것: 죽은 시점에 알림이 나갔지만 알림 기록(`notifications`)이 커밋되지 않았으면(문장 12~13) 재시작 뒤 같은 첫 알림이 한 번 더 나간다 — 늦게 나가는 것보다 두 번 나가는 쪽을 택했다. 상황 행이 커밋되기 전에 죽으면(문장 1~4) 읽기가 사라지지만, 재시작 뒤 재동기화가 현재값을 다시 흘리므로 센서가 아직 이상이면 그때 상황이 열려 알림이 나간다(HA 에 닿는 동안).
- 확인: `tests/test_orphan_situation_recovery.py`. 문장 단위 스윕: `PYTHONPATH=$PWD .venv/bin/python -m experiments.e14_guardian_latency.killsweep --category gas door` 가 종료 코드 0 이어야 한다.

### 오래 묵은 고아 상황을 복구하면 첫 알림 직후 보호자 전달이 나간다 (해결됨 2026-11-12, 결정 0017)

- 증상: 며칠 전에 열린 채 한 번도 알리지 못한 가스 상황이 재시작 때 복구되면, 거주자의 첫 알림이 나간 뒤 약 5초 만에 보호자 전달이, 약 300초 뒤 119 안내가 나갔다. '거주자 먼저, 90초 뒤 보호자' 가 무너진다.
- 원인: 사다리의 모든 시각(`_plan_next`·`_fire_ladder` 의 `realerts_due`·`forward_due_at`·`guidance_due_at`)이 `situations.opened_at` 에서 센다. 복구가 첫 알림을 보내는 시각과 `opened_at` 의 간격에는 상한이 없다.
- 대응: `escalation_ladders.anchor_at`(nullable, 마이그레이션 v4)을 더했다. 기준 = `anchor_at or opened_at`(`LiotService._ladder_anchor`). `_recover_situation` 이 (a)·(b) 에서 '복구 전에는 알림 기록이 없었고 복구 뒤에는 있고(= 첫 알림이 지금 나갔다) 열린 지 90초(`GUARDIAN_FORWARD_AFTER`)를 넘었다' 일 때만 `anchor_at = 지금` 으로 사다리를 만든다. 기준은 사다리를 만들 때 한 번 정해져 재시작(`_rearm_ladders`)에도 유지되고 `update_ladder` 로는 바꿀 수 없다. 보호자·119 메시지의 `at` 은 기준이 아니라 사실인 `opened_at` 그대로다.
- 함정: '지금 보냈다' 는 송신 반환값이 아니라 DB 의 알림 기록 유무(전·후 `situation_notified`)로 읽는다 — (b) 는 `dispatch` 안에서 보내고, 게이트가 막은 경우(헌장 OFF·음소거)는 보낸 게 없어 거주자 우선 창이 성립하지 않으므로 기준을 옮기지 않는다(동의한 보호자 전달이 유일한 안전망 — 결정 0013). 송신이 실패한 복구도 옮기지 않는다: 그 첫 알림은 살아 있는 U5 재시도로 늦게 나간다.
- 남는 한계(오래 묵은 고아 + 복구 송신 실패): 기준이 None 이라 `next_fire_at` 이 과거에 잡힌다. 거주자 첫 알림 재시도와 보호자 전달이 다음 사다리 틱(약 5초 안)에 같은 틱으로 나간다 — 이전의 '재시도는 30초 간격' 표현은 첫 재시도에는 맞지 않는다. 거주자 먼저 90초는 이 경우 지켜지지 않는다.
- 남는 한계(죽는 자리): 복구의 송신은 성공했는데 `create_ladder` 전에 또 죽으면 다음 재시작은 (c) 경로로 가서 기준이 None 이고 보호자 전달이 즉시 나간다. 창이 좁다(송신 → 알림 기록 → 사다리 행 사이).
- 결정 0013(헌장 OFF 와 보호자)은 D2·D4 브랜치와 함께 들어온다 — 이 항목의 참조는 병합 때 연결된다.
- 확인: `tests/test_orphan_situation_recovery.py`(D5 시험들), `tests/test_migration_v4.py`. 열린 시각 기준 시험(`test_late_restart_keeps_the_timing_anchored_to_the_open_time`, (c) 경로)은 그대로 통과해야 한다.

### 재알림은 살아 있는 nonce 를 다시 쓴다

- 증상: 재알림마다 새 nonce 를 발급하도록 바꾸면 첫 알림의 '괜찮아요'가 403 이 된다.
- 원인: 한 제안에 살아 있는 nonce 는 하나다. 새로 발급하면 앞선 알림의 버튼이 모두 무효가 된다.
- 대응: 재알림은 기존 nonce 를 그대로 쓰고, 없을 때(재시작 뒤)만 발급한다.

### 경고 상황을 거절하면 다음 에피소드 첫 알림이 막힌다

- 증상: 누수 알림을 '거절'로 끈 뒤 같은 센서의 다음 누수 상황은 첫 알림이 오지 않고, 10분 뒤 재알림으로 처음 왔다(2026-11-12 이전).
- 원인: 거절은 사다리를 멈추는 동시에 제안을 `dismissed` 로 바꿔 30일 거절 이력에 넣었다. 키(`능력:행동:엔티티:카테고리`)에 상황 id 가 없어 '이 상황'과 '이 센서 30일'을 가르지 못했고, 최근 거절 게이트는 위험 파급도만 우회한다. 재알림 게이트는 거절 이력을 보지 않아 10분 뒤 재알림만 나갔다.
- 대응(결정 0015): `recently_rejected_keys` 가 `situation_id IS NOT NULL` 인 행을 뺀다. 거절은 그 상황의 사다리만 멈추고 게이트는 그대로다(음소거는 경고 상황에도 적용). 30일 조용히 하려면 음소거를 쓴다. 비상황 제안의 30일 거절 억제는 그대로이며 `tests/test_reject_situation_scope.py` 가 둘을 나란히 고정한다.

### 헌장 OFF 는 보호자 전달을 막지 않는다

- 증상: 전면 OFF 상태에서 가스 상황이 나면 거주자에게는 아무것도 가지 않는데 90초 뒤 보호자에게 전달된다.
- 원인: 헌장은 알림 게이트·재알림·거주자 119 안내만 본다. 보호자 전달과 보호자 119 안내 경로는 동의와 하한만 본다.
- 대응(결정 0013): 이 동작을 유지하고 결정으로 고정했다. 헌장은 거주자 알림을, 동의는 가족 호출을 다루며, 거주자가 알림을 끈 집에서는 동의한 가족 전달이 유일한 안전망이다. 헌장 OFF 를 보호자 경로에 연결하는 코드를 넣지 않는다. `tests/test_charter_guardian.py` 가 거주자 0건 · 90초 보호자 전달 1건 · 보호자 119 안내 1건을 고정한다.

### 열린 안전 상황 동안 편의 제안이 나가거나 실행될 수 있다

- 증상: 능동 틱이 판정하는 사이 가스 신호가 오면 가스 첫 알림이 먼저 나가고, 가스 이전 스냅샷으로 만든 편의 제안이 그 뒤에 발송·자동 실행될 수 있었다.
- 원인: `dispatch`·`_try_execute` 는 열린 상황을 보지 않는다. 편의 제안의 출처로 가르려 해도 제안선 후보에는 `__origin__` 이 없다(`proposal_lines.py`).
- 대응(결정 0016): `run_tick` 이 컨텍스트 변수 `_COMFORT_TICK`(불리언 출처 표식)을 걸고, `dispatch` 가 **디스패치 시작·자동 실행 직전·폰 발송 직전** 에 `_comfort_hold()` 로 열린 상황을 다시 읽는다. 열린 상황이 하나라도 있으면 자동 실행 금지, 하한(`severity_floor`)이 CRITICAL 인 상황이 있으면 폰 발송도 보류(영속만 하고 DIGEST, audit `comfort_held_open_situation`, `DispatchResult.held`). 보류 수준을 `run_tick` 에서 한 번만 정하면 안 된다: 디스패치가 DB 를 기다리는 사이 열린 상황을 놓쳐 IMMEDIATE·자동 실행이 나간다(검토자가 실제 aiosqlite 양보만으로 재현, `tests/test_comfort_hold_open_situation.py` 의 k 훑기 시험). 각 확인 바로 뒤 실행·송신까지 await 를 두지 않는다 — 그 사이에 await 를 넣으면 같은 틈이 다시 열린다. 마지막 확인에서 보류하면 이미 쓴 nonce 를 버리고 예산을 되돌린다. 보류분은 `run_tick` 이 `_prop_cell` 에서 뺀다 — 남으면 만료가 `_apply_expired_signals` 를 거쳐 비선호 셀 학습이 된다(출처별 수락률 분모에는 들어간다). 표식을 인자로 만들지 않은 이유: 실험 하네스가 `dispatch(proposal)` 시그니처의 서브클래스를 두고, 인스턴스 속성이면 디스패치가 await 하는 사이 끼어드는 상황 알림 태스크가 표식을 물려받는다(컨텍스트 변수는 태스크 단위). 상황이 닫히면 보류는 풀리고 재발송은 하지 않는다. `standards.md` 의 '파급도 없는 제안의 결과를 바꾸지 않는다'의 예외다.

### 보호자 확인 버튼은 피드백 수신구가 밖에서 닿아야 생긴다

- 증상: 보호자 알림에 'Ack' 버튼이 없거나, 눌러도 응답이 없다.
- 원인: 버튼 URL 은 `LIOT_NTFY_FEEDBACK_URL` 에서 만든다. 값이 없으면 버튼이 없다. 서명 키가 개발 키면 수신구가 열리지 않는다. 보호자 폰은 집 밖에 있으니 이 URL 이 집 밖에서 닿아야 한다.
- 대응: 실제 비밀키 + 밖에서 닿는 피드백 URL(프록시·터널) 둘 다 갖춘다. 그 전까지 보호자 쪽에서는 사다리를 멈출 수 없고, 거주자 응답이나 정상 복귀로만 멈춘다.

### 거주자 '해소됨' 알림은 제안이 아니다

- 증상: 해소 알림의 제안 id 로 DB 를 찾으면 없다.
- 원인: 해소 알림은 응답할 행동이 없는 정보 알림이라 영속하지 않는다(수용률·대기 목록에 섞이지 않게). 송신 기록(`notifications`)에만 남는다.
- 대응: 해소 여부는 `situations.closed_at` 과 `guardian_forwards` 의 `resolved` 로 확인한다.

## 실행

### 되돌리기의 역동작은 여는 방향 금지 목록을 다시 본다

- 증상: 탭 한 번으로 승인한 밸브 잠그기·도어락 잠그기의 되돌리기 요청이 `ExecutionDenied` 로 거부되고, HA 호출은 하나도 나가지 않는다.
- 원인: 되돌리기는 닫기 → 열기, 잠그기 → 풀기 역동작 표를 쓴다. 그래서 역동작이 `valve.open`·`lock.unlock` 이 되는 경우는 실행기 두 곳(실제·가짜)에서 호출 전에 막는다. 서비스는 실행이 성공할 때마다 이전 상태를 저장하므로, 이 막기가 없으면 되돌리기가 집을 연다.
- 대응: 역동작 표나 실행기의 되돌리기를 고칠 때는 `test_haexecutor_undo_never_opens_the_home` 가 실패하지 않는지 먼저 확인한다. 막기를 지우면 정확히 그 테스트가 실패한다.

### 데몬과 관제실이 다른 DB 파일을 볼 수 있다

- 증상: 관제실에서 거주자·보호자·동의를 입력했는데 데몬이 반영하지 않는다.
- 원인: 기본 경로 `liot.db` 는 현재 작업 디렉터리 기준이다. 관제실 서버는 시작할 때 저장소 루트로 `chdir` 하지만, 데몬은 실행한 위치를 그대로 쓴다.
- 대응: 두 프로세스 모두 `LIOT_DB_PATH` 를 같은 절대 경로로 준다. 확인: 데몬 시작 로그의 `db=` 값과 관제실의 DB 파일 경로가 같아야 한다. 같은 파일이면 거주자·동의 변경은 재시작 없이 다음 상황·다음 전달부터 반영된다(매번 DB 에서 읽는다).

### aiosqlite DEBUG 로그에 비밀 토픽이 찍힌다

- 증상: 디버깅하려고 로깅을 DEBUG 로 켰더니 보호자 등록 순간 토픽이 로그에 나온다.
- 원인: aiosqlite 는 DEBUG 에서 실행할 함수(SQL 과 인자를 묶은 partial)를 그대로 찍는다.
- 대응: `logging.getLogger("aiosqlite").setLevel(logging.INFO)` 이상으로 둔다. DEBUG 로그 파일을 공유하지 않는다.

### 새 안전 테이블은 테넌트 스캐너 밖이다

- 증상: `assert_no_null_tenants` 가 통과해도 거주자·보호자·상황 테이블의 `home_id` 는 검사하지 않았다.
- 원인: 스캐너와 `ScopedRepo` 의 테넌트 목록은 버전 1·2 테이블만 담는다. 버전 3 테이블은 DB CHECK(빈 문자열 금지)로 막고, 안전 저장소는 SQL 에 `home_id` 조건을 손으로 넣는다. 일부 조회(상황 id·거주자 id 로 찾기, 열린 사다리 전체)는 집 조건이 없다.
- 대응: 새 쿼리를 쓸 때 집 조건을 직접 넣고, 서비스가 사다리처럼 집 조건 없이 읽는 곳은 결과의 `home_id` 를 다시 비교한다(사다리 루프·보호자 확인이 그렇게 한다).

## 체크리스트

### 새 안전 카테고리를 더할 때

1. `liot/core/risk.py` 의 내장 집합(또는 런타임 등록)에 넣는다.
2. `config/severity/situations.yaml` 에 (피해 종류, 시간, 이상 규칙) 행을 넣는다. 행이 없으면 위험 + 불리언 규칙이 된다.
3. `liot/layers/l4_execution/escalation.py` 의 상황 종류 라벨에 한국어 라벨을 넣는다(없으면 "안전 상황").
4. HA device_class 매핑이 필요하면 브리지 매핑에 넣는다.
5. 검증: 표 칸 테스트, 매핑 행 테스트, `assert_execution_gated()`, 그리고 그 카테고리 이상 신호 하나가 즉시 발송되는 서비스 테스트.

### 알림 페이로드에 값을 더할 때

1. 기기·방·근거·특성이 아닌지 확인한다.
2. 계약 모델 필드 → egress 허용 키 → transport 헤더·본문 순서로 고친다.
3. 정확한 집합 테스트 세 개를 의도적으로 고친다.
4. 검증: `make check`, 그리고 보호자·거주자 페이로드에 금지 필드가 없다는 서비스 테스트가 통과하는지.

### 결정 모델을 바꿀 때

1. `~/models/judge/` 에 GGUF 를 두고 `bench/risk/models.yaml` 에 행을 넣는다.
2. `run_bench.py run --model <key>` → `report`. 조용한 기계에서 잰다(`uptime` load average 확인).
3. 2회 동일·p95·판독 오류·과잉 올림을 본다. 라벨이 draft 인 동안에는 추천만 한다.
4. 운영에 붙일 때 서버 파일과 `LIOT_DECISION_MODEL` 이름을 맞춘다.
