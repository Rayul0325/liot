# 미해결 문제

심각한 것부터 적는다. 각 항목: 조건 → 증상, 파급 범위, 지금 못 고치는 이유, 가능한 접근.

## 집을 여는 실행이 가능한 것

### HA 연결이 끊기면 다시 붙지 않는다

- 조건 → 증상: 데몬이 도는 중 HA WebSocket 이 닫히면(HA 재시작·네트워크 단절) `websockets` 의 연결 종료 예외가 스트림 밖으로 올라가 데몬 프로세스가 끝난다. 형식 오류로 스트림이 끝나는 경우에는 프로세스는 살아 있고 능동 틱만 돌며 센서는 더 받지 않는다. 어느 쪽도 거주자에게 알리지 않는다.
- 파급: 그 뒤의 가스·연기·누수 이상이 전혀 알려지지 않는다. 열린 사다리도 데몬과 함께 멈춘다(다시 띄우면 재무장된다).
- 지금 못 고치는 이유: 재연결 정책(대기 간격, 끊김을 거주자에게 알릴지, 끊긴 동안의 상태를 어떻게 다시 맞출지)은 소유자 결정이 필요하고, 이번 작업 범위 밖이다.
- 접근: 스트림 루프에 지수 대기 재연결 + 재연결 직후 `get_states` 로 카테고리·현재 상태 재동기화. 일정 시간 이상 끊기면 거주자에게 '감시 중단' 알림. 프로세스 감시자(launchd)로 재시작.

### 실행 중에 HA 에 추가한 안전 센서는 침묵한다

- 조건 → 증상: 데몬 시작 뒤 HA 에 `binary_sensor.<새 가스 센서>` 를 추가하면, 그 엔티티는 카테고리 맵에 없어 도메인 접두사 `binary_sensor` 로 분류되고 비안전 관찰로 침묵한다.
- 파급: 새 안전 센서가 재시작 전까지 동작하지 않는다.
- 지금 못 고치는 이유: 카테고리 맵을 실행 중에 바꾸면 열린 상황·재현 키와의 관계를 정해야 한다. 범위 밖.
- 접근: 모르는 엔티티의 첫 `state_changed` 에서 `attributes.device_class` 로 즉석 분류하거나, HA `entity_registry_updated` 를 구독해 맵을 갱신.

### 경고 상황을 거절하면 같은 센서의 다음 상황 첫 알림이 막힌다

- 조건 → 증상: 거주자가 경고 파급도 상황 알림(문·누수·도어락·오븐·고온·수도)에 '거절'을 누른 뒤 30일 안에 같은 엔티티에서 새 상황이 열리면, 첫 알림이 `SUPPRESS` 되고 첫 푸시는 10분 뒤 재알림으로 처음 나간다(2026-10-19 문 열림으로 재현: 두 번째 에피소드 `SUPPRESS`, +10분에 1건).
- 파급: 경고 상황이 최대 10분 늦게 알려진다. 위험 상황(가스·연기, 취약 거주자 집의 경고 상황)은 영향이 없다.
- 지금 못 고치는 이유: 명세는 위험 상황만 최근 거절을 우회한다고 정했다. 경고 상황에서 거절을 '이 상황만 끄기'로 볼지 '30일 동안 그만'으로 볼지는 소유자 결정이다.
- 접근: 상황 알림의 거절은 거절 이력에 넣지 않거나(사다리 확인만), 상황 알림 키를 에피소드 단위로 바꾼다. 거주자 안내에서 '괜찮아요' 를 권하는 것으로 당장 피할 수 있다.

### ntfy 송신이 이벤트 루프를 붙잡는다

- 조건 → 증상: ntfy 서버가 느리거나 닿지 않으면 송신 하나가 최대 `LIOT_NTFY_TIMEOUT`(기본 10초) 동안 동기로 막는다. 그동안 다음 센서 신호 처리, 사다리 루프, 피드백 수신구가 모두 멈춘다. 보호자 전달은 보호자 수만큼 이어진다.
- 파급: 두 번째 안전 상황(예: 가스 직후 연기)의 첫 알림이 앞 송신의 제한시간만큼 늦는다.
- 지금 못 고치는 이유: 비동기 transport 로 바꾸면 이중 확인 표식·nonce 발급 순서(발급과 표식 사이에 스윕이 끼지 않게)를 다시 검증해야 한다. 범위 밖.
- 접근: 송신을 스레드로 보내거나 비동기 HTTP 클라이언트로 바꾸고, 표식을 발급 전에 세우는 순서를 테스트로 고정.

### 시간대 버킷이 UTC 기준이다

- 조건 → 증상: 시간대(morning·day·evening·night)를 UTC 시로 정한다. 한국(UTC+9)에서는 07–15시가 night 다. 야간 정숙 게이트·야간 규칙(조명·미디어 하한 상향)이 낮에 걸리고 실제 밤에는 안 걸린다.
- 파급: 컴포트 알림의 억제·하한이 시간을 틀린다. 안전 알림은 불씨라 야간 게이트를 지나므로 영향이 없다.
- 지금 못 고치는 이유: 테스트·관제실 시각 표·능동 규칙이 모두 UTC 버킷을 전제로 고정돼 있어, 바꾸면 기존 재현 키(스냅샷 해시의 시간대)가 바뀐다. 소유자 결정 필요.
- 접근: 집의 시간대 설정을 두고 버킷만 로컬 시각으로 계산.

### 장애 중 실패한 거주자 재알림은 다시 보내지 않는다

- 조건 → 증상: 재알림 송신이 실패해도 사다리 단계는 넘어간다. 경고 상황은 재알림 3회 한도가 실패로 소진될 수 있다.
- 파급: ntfy 장애가 끝난 뒤 경고 상황의 남은 재알림이 줄어든다. 위험 상황은 1분마다 계속 재알림하므로 영향이 작다.
- 지금 못 고치는 이유: 재시도 정책(실패를 단계로 셀지)은 사다리 규칙 변경이라 결정이 필요하다.
- 접근: 보호자 전달처럼 실패 시 30초 재시도 표식을 남기고 단계를 올리지 않는다.

## 보호자 호출 조건이 모호하거나 오탐이 가능한 것

### 헌장 전면 OFF 인데 보호자에게는 전달된다

- 조건 → 증상: 헌장(`charter_enabled`)이 거짓인 집에서 가스 상황이 열리면 거주자 첫 알림·재알림·거주자 119 안내는 막히지만, 90초 뒤 동의한 보호자에게 전달되고 보호자 119 안내도 나간다(2026-10-19 재현).
- 파급: '모든 알림 끄기'를 고른 거주자의 기대와 다르다. 반대로 막으면 동의한 가족 호출이 헌장 하나로 꺼진다.
- 지금 못 고치는 이유: 명세는 위험 재알림이 헌장 OFF 만 존중한다고 했고, 보호자 경로와 헌장의 관계는 정하지 않았다. 동의 의미에 관한 소유자 결정이다.
- 접근: 헌장에 '보호자 전달 포함 여부'를 따로 두거나, 헌장 OFF 를 보호자 전달의 철회와 같은 뜻으로 정한다.

### HA 의 `unavailable`·`unknown` 이 위험 상황을 연다

- 조건 → 증상: HA 재시작이나 센서 통신 끊김으로 가스·연기 센서 상태가 `unavailable` 이 되면, 정규화 불가 값 = 이상(fail-closed) 규칙으로 위험 상황이 열린다. 90초 안에 정상 값이 돌아오지 않으면 동의한 보호자에게 '가스 누출'로 전달된다. 문·누수 등은 경고 상황이 열린다.
- 파급: 가족에게 거짓 경보가 간다. 반복되면 알림 신뢰가 무너진다.
- 지금 못 고치는 이유: '센서를 못 읽음'을 별도 상황(예: 센서 고장)으로 볼지, 위험으로 볼지는 안전 정책 결정이다. 지금 동작은 명세의 fail-closed 그대로다.
- 접근: `unavailable`·`unknown` 을 별도 '감시 불가' 상황으로 분리해 거주자에게만 알리고 보호자 경로에서 뺀다.

## 측정·모델

### 시험 세트 라벨이 초안이고 지연 측정을 믿을 수 없다

- 조건 → 증상: `bench/risk/labels.yaml` 은 `status: draft`(에이전트가 표 규칙으로 만든 초안)다. 지연 측정 때 기계 load average 가 약 10 이었고 같은 모델 안에서 처리량이 약 600 과 1900 tok/s 로 갈렸다. 필수 조건(두 질문 p95 < 1.0초)을 통과한 모델이 없다.
- 파급: 기본 결정 모델을 정할 수 없다. 운영 `LIOT_DECISION_MODEL` 기본 이름은 선정 결과가 아니다.
- 지금 못 고치는 이유: 라벨 확정은 소유자 검토가 필요하고, 재측정은 조용한 기계가 필요하다.
- 접근: 라벨 확정 → `raw/` 를 옮기고 재측정 → 선정 기준 적용.

### 벤치가 잰 신호를 운영 경로는 보내지 않는다

- 조건 → 증상: 벤치는 맥락 요약 자리에 한국어 상황 문장(예: "오븐 안에서 연기")을 넣는다. 운영 경로의 맥락 요약은 `"[day] 1 signals; changed=1; safety=gas; trigger=sensor_reading"` 같은 집계 템플릿뿐이다.
- 파급: 벤치의 '올려야 할 때 올린 비율'·주입 버팀은 운영 성능을 대표하지 않는다. 운영에서 모델은 카테고리·시간대·후보 행동만 보고 판단한다.
- 지금 못 고치는 이유: 운영 맥락에 자유 텍스트를 넣으려면 그 출처·가명화·주입 방어를 새로 설계해야 한다.
- 접근: 벤치에 '운영과 같은 집계 요약' 변형을 추가해 두 조건을 함께 잰다.

### 모델이 기기를 `PERSON_1` 로 본다

- 조건 → 증상: egress 가명화가 `device` 키를 사람 계열 토큰으로 바꿔, 모델 입력이 `"device": "PERSON_1"` 이다.
- 파급: 기기를 사람처럼 부르는 토큰이 판단을 흔들 수 있다(측정되지 않음).
- 지금 못 고치는 이유: 가명 규칙은 모든 LLM 목적지의 공통 경로라 바꾸면 기존 측정과 재현 키가 달라진다.
- 접근: 기기 키 전용 `DEVICE_n` 토큰을 두고 벤치를 다시 돈다.

### 판단 재현 키가 결정 모델 프롬프트를 담지 않는다

- 조건 → 증상: 결정 백엔드·ollama 백엔드의 프롬프트 상수를 바꿔도 판단 행의 `bundle_id` 가 그대로다. `bundle_id` 는 프롬프트 레지스트리의 기본 판정 프롬프트와 규칙셋 버전·모델 id 로만 만든다.
- 파급: 프롬프트가 바뀐 전후의 판단을 저장된 행만으로 구분할 수 없다(재현성 불변식의 빈틈).
- 지금 못 고치는 이유: 백엔드별 프롬프트를 레지스트리에 등록하면 기존 행의 `bundle_id` 계열이 바뀐다. 범위 밖.
- 접근: 백엔드가 자기 프롬프트 sha 를 내고 판정기가 번들 정책에 넣는다.

### ollama 의 qwen3.5 가 항상 비가용이다

- 조건 → 증상: `LIOT_LLM_BACKEND=ollama` + qwen3.5 면 모델이 JSON 을 `thinking` 에 넣고 `response` 를 비워, 모든 판정이 `LLMUnavailable` → degraded 다.
- 파급: 그 모델로는 Gate2 가 사실상 꺼진다(하한은 유지되므로 안전은 그대로).
- 지금 못 고치는 이유: 결정 모델이 기본 경로가 되면서 ollama 수정 여부는 별도 소유자 결정으로 남겼다.
- 접근: ollama 요청에 `"think": false` 를 넣는다.

## 개인정보·저장

### aiosqlite DEBUG 로그에 보호자 토픽이 찍힌다

- 조건 → 증상: `aiosqlite` 로거가 DEBUG 이면 SQL 인자를 담은 실행 함수 표현이 로그에 찍힌다. 보호자 등록 순간 비밀 토픽이 그대로 나온다.
- 파급: 로그를 본 누구나 그 보호자 채널로 알림을 보내거나 받을 수 있다.
- 지금 못 고치는 이유: 라이브러리 동작이다. 앱에 로깅 설정 지점이 따로 없다.
- 접근: 진입점에서 `aiosqlite` 로거를 INFO 이상으로 고정하고, 토픽을 해시만 저장하는 방식(구독 URL 은 등록 응답에서만)을 검토.

### 새 안전 테이블이 테넌트 스캐너 밖에 있다

- 조건 → 증상: `ScopedRepo` 의 테넌트 테이블 목록과 `assert_no_null_tenants` 는 버전 1·2 테이블만 본다. 거주자·특성·집 설정·보호자·동의·상황·사다리·전달 테이블은 빠져 있다. 안전 저장소는 SQL 을 직접 쓰고, 상황 id·거주자 id 로 찾는 조회와 열린 사다리 목록은 집 조건이 없다.
- 파급: 지금은 집 하나라 실제 누출은 없다. 집이 둘 이상이 되면 한 집의 상황·사다리를 다른 집 서비스가 읽을 수 있다(서비스가 결과의 `home_id` 를 다시 비교하는 곳에서만 막힌다).
- 지금 못 고치는 이유: 단일 집 운영이고, 스코프 래퍼로 옮기면 안전 저장소 전체를 다시 써야 한다.
- 접근: 테넌트 목록에 새 테이블을 넣고(빈 home_id 는 DB CHECK 가 이미 막는다), id 조회에 집 조건을 더한다.

### 데몬과 관제실이 다른 DB 를 볼 수 있다

- 조건 → 증상: `LIOT_DB_PATH` 를 주지 않으면 기본 `liot.db` 가 작업 디렉터리 기준이다. 관제실 서버는 시작 때 저장소 루트로 이동하고 데몬은 실행 위치를 쓴다. 다른 위치에서 띄우면 관제실에 입력한 거주자·보호자·동의가 데몬에 없다.
- 파급: 취약 거주자 가산과 보호자 전달이 조용히 빠진다.
- 지금 못 고치는 이유: 기본값을 절대 경로로 바꾸면 기존 설치의 DB 위치가 바뀐다. 결정 필요.
- 접근: 기본값을 저장소 기준 절대 경로로 바꾸거나, 데몬 시작 로그에 DB 절대 경로와 거주자 수를 찍는다.

## 기능 공백·불일치

### 탭 한 번 조치를 만드는 경로가 데몬에 없다

- 조건 → 증상: 가스 상황이 열리면 상황 알림(`alert`) 하나만 만든다. 밸브 잠그기·도어락 잠그기 제안은 명시 행동을 준 앱 호출(테스트·실험실 이벤트)로만 생긴다. 탭 한 번 예외는 구현·검증됐지만 데몬에서는 쓰이지 않는다.
- 파급: 위험 상황에서 거주자가 탭 한 번으로 밸브를 잠그는 흐름이 실제로는 없다.
- 지금 못 고치는 이유: 어떤 상황에서 어떤 조치를 함께 제안할지(가스 → 그 집의 어느 밸브), 실행 옵트인과의 관계는 소유자 결정이다.
- 접근: 상황 카테고리 → 권장 안전 조치 매핑을 설정에 두고, 같은 상황 id 로 조치 제안을 함께 만든다.

### 관제실 실험실에는 파급도가 나오지 않는다

- 조건 → 증상: `/api/simulate` 는 앱 단독 경로(상황 판정 없음)를 써서 가스 이벤트에도 판단·제안의 파급도가 늘 없다. 화면의 파급도 칸은 '없음'으로 보인다. 파급도 표시는 테스트에서 값을 끼워 넣었을 때만 확인됐다.
- 파급: 시연에서 이번 기능(두 축·가산·보호자 조건)을 실험실로 보여 줄 수 없다. 관제실에 입력한 거주자도 실험실 판정에 반영되지 않는다.
- 지금 못 고치는 이유: 실험실은 요청마다 메모리 앱을 만들고 DB 를 쓰지 않는다. 상황 에피소드는 DB 가 필요하다. 범위 밖.
- 접근: 실험실 이벤트에 파급도 표 계산만 적용하고(에피소드 없이), 거주자 가산은 안전 설정 DB 의 불리언을 읽는다.

### 거주자 '해소됨' 알림에 눌러도 안 되는 버튼이 붙는다

- 조건 → 증상: 해소 알림은 nonce 없이 만들어지는데, 파급도 라벨이 있어 transport 가 수락·거절·괜찮아요 버튼을 붙인다. 누르면 `403 stale or already-used link`.
- 파급: 거주자 혼란. 안전에는 영향이 없다.
- 지금 못 고치는 이유: transport 의 버튼 규칙(파급도 라벨 = 상황 알림)을 바꾸면 페이로드 계약 테스트를 함께 고쳐야 한다. 범위 밖.
- 접근: 해소 알림임을 알리는 표지를 두고 버튼을 빼거나, 버튼 없는 요약 형식으로 보낸다.

### '기록만' 칸의 상황은 묶이지 않고 즉시 나간다

- 조건 → 증상: 명세는 기록만 파급도의 첫 알림을 묶음으로 보낸다고 했지만, 상황 알림은 늘 불씨라 게이트가 즉시 발송한다(세기 2). 현재 표에는 기록만으로 가는 안전 카테고리가 없어 실제로는 일어나지 않는다.
- 파급: 표를 고쳐 기록만 칸을 쓰는 순간 드러난다.
- 지금 못 고치는 이유: 쓰는 곳이 없고, 묶음 경로를 상황 알림에 열면 Safety-Never-Silent 와의 관계를 정해야 한다.
- 접근: 기록만 상황은 제안 없이 기록만 남기도록 명시한다.

### 기존 설명 문서 일부가 코드와 다르다

- 조건 → 증상: 저장소의 기존 설명 문서 몇 곳이 지금 코드와 다르다.
  - `docs/pipeline-overview.md` 의 위험도 표가 DUSK 를 '노을'로 적는다. 코드·화면은 '땅거미'다.
  - `MODULE_SPEC.md` 의 마이그레이션 요약이 `LATEST_VERSION = 2` 라고 적는다. 코드는 3 이다.
  - `MODULE_SPEC.md` 의 egress 요약이 `NTFY_ALLOWED_KEYS` 를 7개로 적고, `NotificationPayload` 요약에 `severity_label` 이 없다. 코드는 11개 키이고 필드가 있다.
- 파급: 그 문서를 믿고 키·버전을 가정한 작업이 틀린다(특히 허용 키 집합은 정확한 집합 테스트가 고정한다).
- 지금 못 고치는 이유: 두 문서는 소유자가 직접 관리하는 설명 자료라 갱신을 소유자 검토에 맡긴다.
- 접근: 위 세 곳을 코드 값으로 고친다.
