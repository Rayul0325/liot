# 0014. HA 연결은 같은 프로세스 안에서 다시 붙고, 붙을 때마다 현재 센서값을 다시 맞춘다

- 날짜: 2026-11-12
- 상태: 채택

## 맥락

- HA 웹소켓이 닫히면 `ConnectionClosed` 가 스트림 밖으로 올라가 `run` 의 gather 가 틱·사다리 루프까지 취소하고 프로세스가 끝났다. 형식 오류로 스트림이 조용히 끝나면 프로세스는 살아 있는데 센서를 더 읽지 않았다.
- 시작 때 HA 가 꺼져 있으면 `serve.py` 가 DB 를 연 뒤 HA 호출에서 막혀, aiosqlite 의 비데몬 스레드가 닫히지 않은 채 프로세스가 멈춰 남았다.
- 시작 때(와 연결이 끊긴 사이) 이미 이상인 안전 센서는 `get_states` 값을 버려서 센서가 한 번 더 바뀔 때까지 침묵했다(게이트 1).
- 신호 하나의 예외가 스트림 루프를 죽였다.
- 앞선 시도(`worktree-agent-ace5b98490b2b79f3`, 0d1d698: 끊기면 알리고 종료 코드 75 로 끝내 launchd 가 재시작)는 검토에서 FAIL 이었다. 종료하는 동안 사다리·피드백도 멈춰 열린 위험 상황의 보호자 전달·119 안내가 늦어진다(게이트 1).

## 결정 (소유자 위임 2026-11-12: 「추천대로 다 진행해」)

1. **종료하지 않고 같은 프로세스 안에서 다시 붙는다.** `LiotService.run(ha_factory=...)` 가 감독을 돌린다. 사다리·틱은 HA 와 무관하게 먼저 뜨고(피드백 수신구는 `serve` 가 `run` 앞에서 연다), 감독은 취소로만 끝난다. `run(bridge)` 는 예전처럼 한 번 소비하고 돌아온다(신호별 예외 격리만 추가).
2. **세션 순서**: 인증 → 구독 → (HA 코어 `RUNNING` 대기, 5초 간격·상한 5분, 그동안 스트림은 받는다) → `get_states` → 재동기화 → 버퍼 비우기 → 스트림. 구독이 `get_states` 보다 먼저이고, 요청을 기다리는 동안 도착한 이벤트는 버퍼에 쌓아 순서대로 낸다. 스냅샷과 구독 사이의 상태 변화가 사라지지 않는다.
3. **재동기화**: 안전 카테고리 엔티티의 현재값을 `handle_reading` 에 한 번씩 흘린다(이상 → 정상 → 감시 불가 순). `restored: true` 자리표시자는 건너뛴다. 이 프로세스가 마지막으로 성공적으로 흘린 값과 같은 엔티티도 건너뛴다. 카테고리 맵은 연결마다 다시 만들어 병합하고(앱·ContextBuilder·ProactiveGenerator 셋에 `LiotApp.set_categories`), 복원 자리표시자·부분 스냅샷이 이미 아는 안전 분류를 덮지 못한다.
4. **대기**: 1초에서 두 배씩 60초까지, 연결이 5분 넘게 안정된 뒤에만 1초로 되돌린다. 인증 거부는 5분 대기와 별도 로그(HA IP 차단 회피)이고 끊김으로 센다.
5. **알림(거주자 토픽에만)**: 끊김이 120초에 이르면 '감시 중단'(경고) 한 번 — 연속 120초, 최근 10분 누적 120초, 시작 후 첫 연결 실패 중 먼저 오는 쪽. 중단 알림이 실제로 나간 끊김이 끝나면 '감시 재개'(주의) 한 번. 헌장 OFF 는 존중하고 음소거는 무시하며 보호자에게는 보내지 않는다(결정 0012·0005 의 경계 그대로). `audit_log` 에 `ha_stream_lost`·`ha_stream_restored`.
6. **오류**: 신호 하나의 예외는 로그로 남기고 다음 신호로 넘어간다. 안전 신호였으면 재동기화를 한 번 예약한다(그 신호는 다시 오지 않는다). 재동기화 도중의 실패는 재예약하지 않는다(영구 장애에서 재동기화가 쉬지 않고 도는 것을 막는다).
7. **실행기**는 호출마다 짧은 별도 연결(열기 → 인증 → 호출 → 닫기)을 쓴다. 스트림 소켓과 공유하면 websockets 가 `ConcurrencyError` 를 낸다(기존 잠재 결함). HA 에 닿지 못하면 실행 실패로 닫힌다(조작 안 함).
8. **serve**: DB 를 연 직후부터 끝까지 하나의 try/finally(수신구·DB 닫기). SIGTERM·SIGINT 는 주 태스크를 한 번 취소해 finally 가 돌게 하고 종료 코드 0 으로 끝난다. launchd 는 선택이다.

## 대안

- 끊기면 종료하고 launchd 로 재시작(0d1d698): 종료하는 동안 사다리가 멈춰 게이트 1 과 충돌해 기각.
- 연결마다 재동기화하지 않고 시작 때만: 끊긴 사이 이상이 된 센서가 침묵한다. 기각.
- 카테고리 맵을 교체(병합 아님): HA 기동 중 부분 스냅샷이나 복원 자리표시자가 안전 분류를 비안전으로 덮는다. 기각.
- 스트림과 같은 소켓으로 실행기 호출: 동시 `recv` 로 `ConcurrencyError`. 기각.
- `entity_registry_updated` 구독으로 즉시 분류: 범위 밖(다음 재연결에 반영되는 것까지만).

## 결과

- 끊김 중에도 열린 상황의 재알림·보호자 전달·119 안내는 시각대로 나간다. 새 이상은 HA 가 닿아야 열리고, 그 공백은 '감시 중단' 알림으로 알린다(알림이 나가기 전 120초는 공백이다).
- 재동기화로 끊긴 사이 이상이 된 센서가 붙는 즉시 알림을 낸다(끊김 시간만큼 늦다). 열린 상황은 '이어감'으로 흡수돼 중복 알림이 없다.
- 중단 알림 전송이 실패해도 재시도하지 않고(감사 행에 `notified: false`), 그 경우 재개 알림도 보내지 않는다.
- 감시 판단 상태(`_ha_last_fed`·카테고리 병합맵)는 메모리다. 재시작하면 처음부터 다시 맞춘다.
- 미해결: 틱 루프(`run_tick`)의 예외는 여전히 격리하지 않는다(DB 장애 시 `run` 이 끝난다). 알림 전송은 동기 호출이라 ntfy 가 느리면 루프가 그만큼 멈춘다(기존 한계).
